# JavaRailways 代码审查

仅用于包含 `Core`、`Basic`、`settings.gradle` 和 `.trellis/spec/javarailways` 的本 JavaRailways 仓库及其 worktree。路径均相对仓库根目录。遵守当前 AGENTS.md、用户范围与运行限制；审查请求本身不授权修复、提交、部署或迁移。不要自动创建 Trellis 任务；遵守当前会话的任务选择。

## 先固定范围和证据

- 记录分支、HEAD、比较基线及相关未提交修改；区分 diff 审查、模块审查和全仓审查。并行工作导致源码变化时重核受影响结论，不把不同候选的测试结果拼成一次验收。
- 模块/全仓审查先从 `settings.gradle` 和实际文件建立覆盖清单：生产代码、测试、fixture、构建、公开 API、对应规范与文档。记录未读、已定位、调用链审查、动态验证；文件数和测试数不代表质量或覆盖率。用户举出的类只是例子，不能据此缩小原范围。
- 读目标模块的 `.trellis/spec/` 索引和相关 owner 合同。持久化相关内容先读 `.trellis/spec/javarailways/shared/versioning.md` 和 `ai_tasks/persistence_schema_evolution_rules.md`。未发布格式不擅自升版，不引入旧开发数据的 runtime compatibility。
- 首次执行本 skill 时读 [历史漏检案例](references/missed-findings.md)。历史报告是检查线索，不能直接当作当前缺陷；按符号、调用方、现有合同重新定位，不复用历史行号或临时产物当现状证据。

## 两条审查线都要覆盖

### 行为：沿生产入口追踪完整状态变化

对涉及的功能写出入口 → 校验/准备 → 状态写入 → 发布 → 下游消费 → 保存/清理；逐段确定谁拥有状态，谁能观察它，以及失败时已经改变了什么。跨模块追踪必要消费者，但不因此声称消费者模块已审完。

按实际涉及的领域选择检查；不要求每个小 diff 扫描所有无关子系统：

- **缓冲与发布：** setter 写 active 还是 published？紧接着的 getter 是否仍读旧值？覆盖构造、恢复、换向和结构提交，不只查正常 tick。检查 controller buffer、train frame、mailbox、occupancy、world frame 及 ticket 的各个发布门禁，不能用最终 world frame 未改变证明前面没有发布。close、取消、quiesce、真实 worker 终止是不同合同；扩展回调不能因加锁修竞态而进入可阻塞的核心锁域。
- **身份与所有权：** 区分 UUID、准确注册实例、world、plugin slot、保存 type ID；同 UUID 替换后的旧引用不能删除新对象。检查构造失败、load 失败、正常销毁各自的自有/借用资源；一个扩展清理失败是否截断独立 Core 注销？对外 Future 是否泄漏内部完成权？监听器、指标表、registry、scope 都查释放，不能把注销登记当作资源关闭。
- **值与持久化：** 只读接口不等于不可变值；检查向量、嵌套集合、copy/serializer 入口及旧 snapshot 的别名。沿实际 writer → decoder → restore 检查方向、位置、单位、扩展 ID 唯一性及完整预校验。检查最后一个坏元素失败前是否已写入前面的对象；缺省值与非法值不得混同。
- **几何与方向：** 区分稳定车厢顺序、运营反向、每端 rail facing、canonical 弧长、水平 station、三维弧长和角度单位。组合检查坡度×曲率、反向×接缝、平行偏移×纵断面重建；验证区间中点及插值退化，不能只验证端点。broad phase 必须覆盖 narrow phase 接受的容差；容差内输入转换后不能越过下一层不变量。
- **资源状态机：** 沿普通/换向请求 → reservation → prepare → grant → extend → release/cancel 追踪真实入口。验证环线重复轨道和嵌套区间是否破坏排序/二分前提；上层 guard 不能替代 Basic 公开服务自身合同。检查人工驾驶无 claim 的实际占用、编辑保护以及相关/无关拓扑变化，不用全局 revision 不同代替实际依赖验证。
- **跨层装配：** 快照投影是否保留完整语义？平台是否重读原始 UI 树或 live registry？动态贡献是否参与依赖和提交？公开签名变化是否遗漏 BukkitPluginDev、Java consumer、simulation 或其他宿主路径？模拟通过不证明生产装配一致。

### 工程：检查抽象是否表达当前真实合同

这一轮不能被行为测试绿色替代。分别评估逻辑、可维护/可读性、文档、错误处理、遗留代码、规范一致性、测试有效性。

- 追踪类型/方法/结果分支的**生产者和消费者**，区分生产、开发工具、测试、扩展契约与反射/注册入口。测试仍在调用不证明旧协议应保留；公开能力已有明确保留决策时也不能仅因没有内部 caller 删除。
- 查重复状态、双套算法、无消费者 writer/DTO、不可达错误分支、无用途参数、测试专用策略进入生产基类，以及 nullable 字段能否表示不可能状态。封闭内部集合与真正插件扩展点分别处理。
- 检查 catch 是否把内部不变量失败伪装成插件输入错误、拒绝是否变为成功、dirty 是否错误清除。异常、null、fallback 本身不是缺陷，必须证明违反哪个合同。
- 按实际变化原因和依赖方向评价包/文件职责；高层 Factory/Solver 不应成为基础数学工具的 owner。提取纯计算可保留一个事务/锁/发布 owner；不能仅因文件长就拆成策略框架或多个状态 owner。
- 搜索同类实现和对称路径：construct/load、register/unregister、request/reverse、live/simulation、save/reversed-save。说明是否存在相同遗漏，而非修一个点后推定全类已闭合。

## 用能证伪结论的验证收尾

- 先追踪真实生产链再决定是否需要复现；遵守用户“不运行测试”等限制。纯静态审查明确标注未执行。
- 回归调用真实入口并断言可观察状态、身份、占用及失败后的可重试性。期望值独立于生产计算；避免复制分支、比较同一本地公式、只断言非空、把初始零速度当运动成功。
- 并发检查用确定性 latch/barrier 或已有同步注入；不靠 sleep、随机重跑或新增生产 hook 蒙出竞态。fixture 成对关闭自身 world/coordinator/tick；清理失败保留原失败，不销毁借用资源。
- 有修复授权时，适合的回归应证明旧实现失败、新实现通过；没有实际跑过旧码不得声称红→绿。只读审查需要的临时探针放临时目录。
- 按改动选模块及直接消费者检查，读取实际执行/跳过/失败结果。旧编译产物局部复现、目标源码重编译、完整候选构建、服务器/Folia/客户端验证分开；不以本地测试替代压力、性能或现场证据。

## 交付与停止条件

每个发现提供：严重性与类别、当前位置、具体触发条件、违反合同、真实调用链/可达范围、影响、证据等级和最小处置方向。没有足够证据的列为待验证风险；结构建议与确定行为缺陷分开。不将 API 可构造输入夸大为正常生产已发生故障。

交付同时列明实际覆盖、排除项、未检查区域和验证限制。已读完清单意味着本轮覆盖完成，不等于模块无缺陷；修复后的局部复核也不等于重新全模块审查。历史案例用于主动寻找反例，不设发现数量指标。若仅审查，不改代码；若用户另授权修复，按其批次和顺序实施，保留无关脏文件。
