# 可执行契约编写规则

## 适用范围

新增或实质修改模块、跨层API、基础设施、数值算法、并发模型、缓存、索引或持久化边界时，使用本规则。契约的目标不只是列出接口，还要让不了解实现的人理解模块如何工作，以及哪些内部原理不能在重构中被无意改变。

## 必需结构

对上述non-trivial主题，code-spec至少包含：

1. **状态、范围与触发条件**：区分`CURRENT`、`TARGET`、`TRANSITIONAL`，列出owner与非目标；
2. **模块工作方式**：用一条正常主流程说明输入、权威状态、处理阶段、输出和上下游；
3. **内部机制与关键算法**：描述决定正确性或性能的表示、算法步骤和成立前提；
4. **接口、数据结构与单位**：只把已经冻结的字段写成目标签名，概念草图必须显式标注；
5. **不变量与生命周期**：包括线程owner、publication、revision/epoch、缓存失效和失败后状态；
6. **校验与错误矩阵**：每个拒绝条件、typed结果及允许的mutation；
7. **性能与退化行为**：复杂度、hot path、候选上限、tolerance/迭代上限和fail-safe行为；
8. **Good/Base/Bad cases**：各选择最能区分语义的少量案例；
9. **必需测试与断言点**：覆盖算法边界、失败原子性和性能不变量；
10. **迁移、未决事项与Wrong/Correct**：区分已决定合同和仍需决定的实现。

旧spec不要求仅为统一标题而机械重写；触及其中的non-trivial机制时，必须补齐相关内容。

## 什么内部原理必须记录

满足任一条件就必须简述：

- 替换后可能改变业务或安全正确性；
- 决定渐进复杂度、hot-path成本或内存规模；
- 包含数值tolerance、插值、搜索、迭代上限或退化分支；
- 决定线程可见性、原子publication、rollback或fail-closed行为；
- 使用缓存、索引、派生图或revision失效；
- 表面相似的实现会产生不同结果，例如“左侧区间”与“最近采样点”。

每个机制至少回答：内部表示是什么、算法如何走、依赖什么前提、复杂度如何、失败/退化时返回什么、由哪些测试锁定。不要记录无关紧要且可自由替换的私有细节，例如普通局部变量名或不影响合同的集合实现。

## 文档归属

- package/layer spec拥有实现机制与可执行不变量；
- task `design.md`只给跨模块工作模型、关键取舍和迁移顺序，并链接owner spec；
- `prd.md`只保留目标、需求、验收和非目标；
- `implement.md`只保留批次、依赖、验证和完成状态。

同一算法或错误语义只在owner spec完整定义，其他文档用链接和一句上下文引用，不能复制出多份会漂移的合同。

## 审查清单

- [ ] 新人不读源码能否说明一次正常请求如何经过模块？
- [ ] 能否指出至少一个不能用“看起来等价”的实现替换的算法步骤？
- [ ] 是否写明算法前提、复杂度和退化行为？
- [ ] CURRENT、TARGET与TRANSITIONAL是否可区分？
- [ ] task文档是否链接owner spec而不是复制它？
- [ ] placeholder是否标成概念草图，而没有伪装成冻结API？
