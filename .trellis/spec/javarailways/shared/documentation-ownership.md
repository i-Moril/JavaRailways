# 文档职责与同步规则

## 范围

本文规定维护者契约、公开 API 参考、使用文档与代码导航的分工，不新增业务行为或另一套需求管理系统。
模块职责概览由根 `requirement.md` 管理，具体行为由负责该模块的 spec 定义；实际完成情况必须核对源码、测试及任务记录。

## 四类文档各自回答什么

- **Trellis spec**：供维护者理解“模块怎样工作、修改时不能破坏什么”。记录正常流程、non-trivial 内部算法、单位、不变量、线程/版本边界、失败行为和测试要求，遵守[可执行契约编写规则](../../guides/code-spec-authoring.md)。同一机制只在负责它的 spec 完整定义，其他层链接引用。
- **Dokka**：供 API 使用者查询“公开类型和方法如何调用”。源码 KDoc/Javadoc 负责参数、返回值、单位、错误和使用条件，模块 Dokka 输入负责包级导览；生成 HTML/Javadoc 不是手工维护源。只有 Java/Kotlin `public` 可见性不等于受支持 API，公开范围由模块 build 的 Dokka 配置和对应 API 契约共同确定。
- **网页文档 `docs-site/docs/`**：供玩家、管理员和扩展开发者理解“如何安装、配置、操作和接入”。模块 README 提供本模块的使用入口和链接，不复制完整维护合同。网页可以解释架构，但不能成为另一份会漂移的内部契约。`docs-site` 是独立 Git submodule，修改、验证与提交须单独处理。
- **`.codeabs`**：供代码导航回答“相关实现在哪里”。只保存简短目录地图、入口和关联文件，不保存需求、完整算法合同或验收结论。过时地图须按源码修正，不能将地图中的路径当成仍有生产调用的证据。

Trellis 的 `tasks/` 另管计划、审查台账和历史验证：`prd.md` 写需求与验收，`design.md` 写跨模块取舍，
`implement.md` 写执行状态。任务不是第五份长期 API 文档，完成的稳定规则应链接回负责该机制的 spec。

## 修改一次功能时怎样同步

1. 先检查真实调用链和所属模块；源码与文档冲突时记录差异，不默默用现状取代已批准的目标契约。
2. 规则或关键内部原理改变，更新对应 spec；公开签名/语义改变，同步 KDoc/Javadoc 与 Dokka 公开范围。
3. 玩家配置、命令或扩展接入改变，更新 README 或网页说明；路径移动或代码删除，同步相关导航，不生成整仓无关改动。
4. 更新任务的当前清单和证据。历史批次保留当时的范围、提交和验证结果，已取代的内容明确标注，不继续当作当前缺口。
5. 检查相对链接、命令/字段与当前实现是否一致；只有文档修改时无需重跑 JVM 测试，但不能把历史测试写成本轮运行。

例如，信号树形扫描的按分支遇环停止由 SimpleSignals spec 解释；JS API 的方法语义在其公开参考中说明，
包作者的目录与配置示例放在使用文档；地图只指出扫描实现的位置。不要在四处各维护一份遍历规则。

## 完成状态与验证证据

- `CURRENT` 表示已有实现，`TARGET` 表示目标，`TRANSITIONAL` 必须说明剩余迁移；不能只凭草稿或类型定义宣称功能已完成。
- 源码检查、离线测试、产物打包、真实 Paper/Folia 与客户端验证是不同证据；清单应分别记录，不能用“测试通过”代替游戏内验收。
- 总项包含多个交互或现场验证时，不因其中一个子项完成就整体勾选；已完成能力也不能因现场验证未做而写成“尚未实现”。
- 不维护互相竞争的“最新进度”清单：活动任务顶部汇总当前状态，较早批次作为历史；审查任务链接父任务，不复制其完整功能合同。

## 审查要点

- 内部算法和安全约束是否只有一个负责模块的完整定义？
- 公开签名涉及的类型是否有清楚的契约和文档范围，而非隐藏实现类型？
- 使用说明是否仍描述旧字段、旧 owner 或已删除入口？
- 地图是否只做导航，阶段清单是否区分历史、离线完成和现场未验证？
- 是否保留 docs-site 已有修改，并分别检查根仓和 submodule 的 Git 状态？
