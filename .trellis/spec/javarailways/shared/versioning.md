# 版本号：先确认发布基线，再判断是否升版

本规则是全仓版本决策的前置门槛，适用于持久化格式、配置、extension payload 和相关版本常量。具体编码、迁移与校验方式见[持久化与 Schema 演进](./persistence.md)及[完整政策](../../../../ai_tasks/persistence_schema_evolution_rules.md)。模块契约不得用“存在破坏性变化”跳过本门槛。

## 最重要的规则

**未发布的开发格式直接修正当前模型，不随着开发提交递增 schema version。已发布或用户明确冻结为兼容基线的格式，才进入破坏性变化的升版判断。**

因此，“删了字段”“改了语义”“两次提交分别改了结构”都不能单独证明需要从 `1 → 2 → 3`。

## 先确认什么是基线

修改版本号前，必须确认目标独立边界的已发布格式或用户明确指定的兼容基线，并记录证据，例如发布记录、已分发的格式契约，或用户明确要求保留某批已部署数据。

以下事实不能单独证明存在发布/兼容基线：

- 代码已有本地 commit，或曾合并到某个分支。
- JAR 已构建、测试已通过、fixture 已生成，或任务标记完成。
- 开发服上曾写出文件。
- 当前常量已经是 `2` 或 `3`；数字本身不能证明这些代际曾发布。

不知道是否发布时，不得虚构部署历史，也不得“保险起见先升版”。先查可核实的记录；仍不明确时向用户确认，版本常量保持不动。未涉及版本号的实现工作可以继续，不因此添加猜测性的兼容路径。

## 决策顺序

1. 确认真正的独立持久化边界及其已有版本，不给内部 DTO 或功能变体额外编号。
2. 确认发布/冻结基线。若已确认未发布，直接修改当前形状，保留该边界约定的初始版本（通常是 `1`），同步当前 fixture、样例和文档。
3. 若已有发布/冻结基线，再比较新 reader 能否正确、无猜测地读取该基线数据。
   - 能直接读取，包括新增有明确默认值的字段：不升版。
   - 不能直接读取，存在字段删除、改名、类型/单位/语义或结构变化：只升级最小独立边界。
4. 只有用户、任务合同或已发布兼容政策明确要求时，才新增旧输入支持；写清支持窗口、移除条件，并在 decode/migration 边界单向转为 current model。

开发服数据确实需要保留时，优先使用可审计、可 dry-run、保留恢复点的一次性迁移，而不是永久保留旧开发 reader。版本变更和运行时兼容是两项分别需要依据的决定。

不要把本规则理解成“全仓版本全部改成 1”。已有真实发布基线的边界保留自己的版本；纠正误升版也应单独确认范围，不顺带重置其他模块。

## 不得混用的版本概念

- `schemaVersion` / `formatVersion` 表示独立数据契约，不表示实现进度、重构批次或 commit 次数。
- `revision` 表示数据变更先后，`epoch` 表示运行发布时序；两者都不是 schema version。
- 插件/模型包发布版本有自己的发布流程，不能因内部 schema 改动自动升级，也不能替代 schema version。
- 并存能力使用稳定 `kind/type`；不使用 `V1/V2` 给实现新旧或功能强弱命名。
- 不为未发布的开发阶段建立 `LoaderV1/LoaderV2`、`writeV2()` 或多代并行业务模型。

## 本次问题的反例

SimpleSignals 未发布格式先删除默认进路，再改为两端独立信号规则。这两项可能改变 JSON 的形状和语义，但**不能仅凭先后发生两次破坏性改动，就分别升级 schema 为 2 和 3**。应修正同一个当前格式并保持约定版本；若误升版已经进入代码，另行修正代码、当前 fixture 和文档，不增加读取误升版数据的兼容分支。

此反例说明决策规则，不宣称当前运行代码已经完成版本纠正，也不宣称曾经部署。

## 实施与审查检查表

- [ ] 指出本次涉及的独立边界、当前版本和发布/冻结基线。
- [ ] 若计划升版，给出可核实的发布证据或用户明确要求，不能只列出 breaking change。
- [ ] 未发布格式只更新 current model、fixture、样例和文档，不增加开发代际。
- [ ] 已发布格式的升版只影响最小边界；兼容字段、revision/epoch 和无关模块不连带升版。
- [ ] 新兼容路径有明确授权、支持窗口、移除条件和固定旧输入 fixture。
- [ ] 提交说明分别说明是否改版本、是否支持旧输入，以及理由；未改变版本时不虚构“已部署”。

缺少发布/冻结基线依据的升版，应在审查时拒绝，而不是先提交后解释。
