# 单线单闭塞的双向控制

## 1. 状态与负责模块

CURRENT，已完成离线验证。SimpleSignals 负责双向匹配与入口检查；Basic 继续负责同一资源的互斥、授权和车尾释放。
本批实现一个物理闭塞、两个真实入口和一个共享主信号结果。工具、测距、两端独立规则及单线多闭塞协调不在本批。

## 2. 一列车如何通过

玩家把闭塞标记为双向，仍只保存一条从首端到末端的轨道路径。列车从任一端接近时，
SimpleSignals 把冻结路线与这条路径的正向或反向匹配，生成实际入口的检查声明和路线上的授权下限。
两种方向都申请 `StableInfrastructureResource("simplesignals:fixed-block", blockId)`。
Basic 原子取得完整资源集合；另一列车不能同时持有这个闭塞，即使两车暂时位于不同轨道片段。
车尾离开后使用原有释放队列释放，随后另一方向可以申请。

两端信号机可复用同一主信号结果，另一台使用已有附属设备定义；不重复执行信号规则。
同一灯色不代表两车都取得授权，列车仍必须遵守 Basic 的实际授权。

## 3. 路径反转与匹配方法

闭塞的反向路径由已归一化路径倒序、每段 `facing` 取反得到，canonical AB 的上下界不变。
例如 `rail1 AB → rail2 BA` 的反向是 `rail2 AB → rail1 BA`，不是简单把整条路径标成 BA。
反向路径只在双向闭塞的准备阶段生成。原路径经过既有连续性校验；Core 的拓扑生成器已经拒绝非对称物理连接，
道岔合法连接也来自同一已校验映射，因此不重复验证必然合法的反向连接。运营方向限制仍属于 SimpleATO，不由这里放宽。
它是可丢弃派生值，不增加资源、占用监测区或存档路径副本。

匹配保留既有 rail→block 索引、route metres、交集拼接和完整路线验证。双向闭塞分别匹配两种路径，
每次通过仍须满足完整路径或只在运营路线端点截短，然后才按本次申请范围裁剪。
结果保留本次通过的方向，检查声明从该方向的首段取得 rail/facing，触发位置使用实际入口的 route metres。
从闭塞内部起步仍不生成入口声明；重复经过仍以同一声明 ID 加不同路线位置区分。

## 4. 数据与接口

`FixedBlockDefinition` 新增 `bidirectional: Boolean = false`，同名字段位于原有 `fixedBlocks` 对象内。
省略或 false 保持原单向匹配；true 开启正反向匹配。既有 ID、revision、traversals、资源类型与声明身份不改变。
`CompiledFixedBlock.reverseTraversals` 保存已验证的反向路径，`entryTraversals` 保存一个或两个真实入口；
`FixedBlockRouteWindow.reversed: Boolean = false` 标识本次经过的方向，只用于派生入口，不写入存档。
两端使用相同提前时间、限速和外观结果；下游规则配置仍是该主信号的一份明确规则，不自动推断另一份方向规则。
跨模块继续使用现有 `InspectionDeclaration`、`ContributedRouteResource` 和 Basic 授权接口。

## 5. 版本、线程和释放

开启或关闭双向属于定义修改，必须提高闭塞 revision，并经过原有候选编译、编辑许可和保存事务。
反向几何和编辑影响在工作线程准备，不在物理 tick、规则更新或平台线程重建。
停车折返保留已占用的同一 block token，返程匹配提供新路线上的释放位置；不得先释放再重新争抢。
停在闭塞内部不释放 token，车头通过出口也不单独触发释放。

## 6. 拒绝与安全行为

非法字段类型、越界或不连续路径、revision 未提高、过期拓扑和受保护编辑继续使用原有失败结果。
原路径不能通过既有物理连接验证时拒绝整份候选，保留原存档和发布结果。
已配置信号但尚无有效结果时，两端入口都产生 0 限速；资源拒绝不能扩大授权。

## 7. 性能

设双向闭塞总 traversal 数为 T，反向准备增加 O(T) 时间和空间。占用监测和规则节点数量不增加。
一次路线匹配仍为 O(R + K log K + I log I)，双向候选最多增加一遍方向匹配；不增加全世界扫描或逐 tick 路线投影。
保护区域后继查找继续使用已排序路线窗口，编辑影响按入口轨道索引最多加入两个入口，而不是扫描全部区域×全部闭塞。

## 8. 具体情形

从两端申请：第一列车持有 block token，第二列车的原子申请被拒绝，不留下部分新增资源。
内部站台折返：token 保留，返程重置车尾坐标并使用同一 token 的新释放点；其他列车仍不能进入。
咽喉出口接反向入口：直接后继仍是这一个闭塞，授权下限延伸到返向路线中的闭塞出口或运营终点。

## 9. 必需验证

验证默认单向不变、正反向多轨道混合 facing、完整/裁剪/内部起止及重复经过；检查真正反向入口的 rail/facing 和触发位置。
验证两端读取同一信号结果、缺基线为 0、资源/监测区/规则数量不翻倍。
通过真实 Basic 申请与车尾释放，验证相向互斥、失败原子性、释放后重申请和停车折返保留 token。
验证反向保护区域后继及其编辑保护；固定缺字段 fixture 得到 false，true round-trip 保留，非法类型和未提高 revision 被拒绝。

本批针对性测试 134 项、7 个测试类全部通过；独立审查未发现范围内缺陷。
最终离线 `:SimpleSignals:check :BukkitPlugin:compileSignalApiConsumerJava` 通过：295 项测试、30 个测试类，
零失败、错误或跳过，插件 JAR 隔离检查实际执行并通过。实际 Basic 类组合测试验证资源生命周期，
但这不等于完整回库任务或真实 Folia/客户端运行验证，后二者仍未执行。

## 10. 存档与后续边界

默认值明确的新增字段仍使用 schema 1，不新增旧格式适配、别名、迁移器或中间版本。
不得把同一闭塞拆成两个方向资源，也不得为支持两个入口引入第二套释放队列或信号循环求解。
两端独立输出不是当前共享显示关系的强制限制；如以后需要，再单独设计方向规则。
单线多闭塞的整段方向协调仍在 TODO 中，本批不开设整段独占资源或方向锁。
