# SimpleSignals 如何把信号状态显示成模型

## 1. 这份设计负责什么

本文是尚未实现的设计草稿（`TARGET / DESIGN DRAFT`），当前没有信号模型渲染功能。
它描述 SimpleSignals 如何连接自己的信号状态与模型，而不是重新定义进路、限速或资源管理。
其中 `default` 的名称、适用范围和选择规则已经确认；完整模型包格式及摆放配置仍待审查。

SimpleSignals 负责模型包、摆放位置、外观映射，以及何时创建或关闭模型。
主插件提供通用的构造和显示能力，见[通用模型 API](../../bukkit-plugin/backend/model-presentation-api.md)。
轨道曲线查询、公开不可变模型定义、普通构造和完整场景应用由主插件提供；
公开模型服务负责跨线程调度。本模块的模型包和信号绑定仍未实现。
SimpleATOBukkit 不负责转发信号画面。

## 2. 从配置到显示的完整流程

1. 玩家为一个信号设备选择模型包、轨道位置、朝向和局部偏移，并配置不同外观对应的模型场景。
2. 加载或编辑配置时，SimpleSignals 检查引用，计算世界坐标和旋转，再取得操作模型的 `ModelHandle`。
3. 信号系统完成一次状态计算后，SimpleSignals 读取完整结果，找出外观确实变化的设备。
4. 对这些设备提交新的模型状态。主插件在正确的 Minecraft 线程上应用显示变化，不阻塞信号计算。
5. 设备删除、世界卸载或插件停用时，关闭相应模型。

信号控制的入口位置，不一定是模型实际摆放的位置。例如，进路预告机可以放在远处，
站台信号机可以放在轨道侧面。不能只根据逻辑入口就假定已经有了模型摆放配置。
目前固定闭塞信号和保护区域信号还没有物理摆放字段；进路显示器虽有轨道位置，也还没有模型绑定配置。

## 3. 哪些机制避免重复计算和错误显示

### 摆放位置只在需要时计算

位置采用轨道 UUID、沿 A 到 B 从 A 端量起的距离（米），以及模型朝向。
SimpleSignals 根据配置决定侧向/高度偏移和是否跟随轨道倾斜，读取不可变曲线后计算世界位置与旋转。
结果可以缓存；只有相关轨道或摆放配置被编辑时才重新计算，不每 tick 重定位全部信号机。

### 外观名由信号插件解释

规则输出的 `modelVariant` 是外观名称。SimpleSignals 将它映射为完整的“动画名 → 场景名”选择，
例如 `lamp -> green`。主插件不理解 G/YG/Y/R 的铁路含义，也不根据模型场景反推限速。

模型包解析后交给主插件的是已经展开的普通部件树，不是列车定义，也不是让显示线程继续读取文件的回调。
树、帧、变换、物品资源和复位行为由[主插件模型契约](../../bukkit-plugin/backend/model-presentation-api.md#4-公开接口与数据)
统一描述；SimpleSignals 不再维护一套相同的通用定义。
外观映射必须是完整场景选择。比如旧外观选择了 `lamp`，新外观没有再为这个部件选择任何动画，主插件应恢复其基础外观，
而不是让旧灯色残留。固定零插值只影响画面过渡，不改变信号计算或列车制动。

### 使用完整状态，而不是一半新、一半旧的结果

`SectionOccupancyRuntime` 先把区间占用、信号输出、进路选择和显示器状态一起替换为新的完整结果，
然后才发出显示通知。这就是这里所说的“发布”：新结果成为读者当前可见的结果，不是网络发送。
显示侧不能提前读取部分新结果，也不能在信号计算回调中操作 Bukkit 实体。

### 只检查受影响的设备

普通信号使用已有的变化 ID 列表。进路显示器使用已有的“入口 → 相关显示器”索引查找候选。
再比较这些设备的实际外观、位置和旋转；只改限速或进路附带信息而画面不变时，不提交显示更新。
因此不需要每次遍历全部设备。

配置增删改、初始加载和世界重载也要触发显示处理，不能只等待列车进入或离开区间。
配置替换时先关闭旧模型。即使旧状态计算的回调稍后才完成，它也只能访问已经关闭的旧操作对象，
不能覆盖新模型。

## 4. 内部处理步骤和数据约定

下面是流程说明，不是已经存在的函数，也不是新增的存档结构：

```text
准备模型绑定：
    检查轨道位置、模型引用和外观映射
    按世界 UUID 和轨道 UUID 取得曲线
    按 A 端起算的弧长取得轨道上的点
    根据朝向和摆放配置计算世界位置与旋转
    保存解析后的绑定、模型定义和位置结果
    读取当前已发布结果；尚无结果时选择模型包的 default
    提交初始完整显示状态

信号系统发布完整结果后：
    遍历本次可能受影响且已配置模型的设备
    读取设备的新状态
    若为 Unavailable，选择模型包的 default
    否则按明确的 modelVariant 查找场景；找不到则报告配置错误，不使用 default 兜底
    若场景、位置和旋转与上次提交相同，跳过
    否则增加该模型的显示序号，提交位置、旋转和场景

设备删除或世界卸载：
    关闭该设备的模型操作对象
```

### 已确认的默认显示规则

只有 **SimpleSignals 模型包**必须显式提供 `default`。它是一份完整的“动画名 → 场景名”选择，
不是主插件通用 `ModelDefinition` 的必填字段，也不要求列车、轨道或其他附属插件采用相同规则。
主插件只接收最终的场景选择，不知道它来自普通外观还是 `default`。

- 初始绑定尚无已发布信号结果，或已有结果为 `SectionSignalState.Unavailable` 时，选择 `default`。
- 有效结果明确给出 `modelVariant` 时，只使用该名称对应的完整场景选择。
  名称没有对应映射属于配置错误，不允许静默回退到 `default`。
- `default` 的内容由包作者决定，可以是红灯、熄灯或其他故障外观；代码不固定灯色或场景名。
  它必须存在且是有效映射；显式空映射 `{}` 表示恢复全部部件的基础外观，不等于缺少配置。
- 内部的 `Unavailable` 状态不改名；它仍表示没有有效信号输出并保持既有 0 限速。
  `default` 只决定画面，不能改变这个安全结果，也不能默认保留上一幅放行画面。
- 正常的 0 速度输出和进路显示器已有的 `noRouteModelVariant` 都是明确的外观选择，
  不能仅因“红灯”或“没有进路”就跳到 `default`。
- 设备已删除、世界已卸载或插件停用时关闭模型，而不是把失效绑定永久保留为默认显示。

### 配置片段草案

以下只展示外观映射，不是可直接加载的完整模型包；当前还没有 YAML 加载器。
`default` 已确定，`variants` 的外层结构是建议写法，完整部件文件、包入口和目录组织另行审查。
示例假设部件树已经定义动画 `lamp` 及其 `dark`、`red`、`green` 场景：

```yaml
default:
  lamp: dark
variants:
  stop:
    lamp: red
  proceed:
    lamp: green
```

这里的 `stop`、`proceed`、`lamp` 和场景名都只是作者选择的名称，没有内置语义。
初始无结果时显示 `lamp: dark`；正常结果为 `proceed` 时显示 `lamp: green`；之后状态变为
`Unavailable` 时重新提交完整的 `lamp: dark`。正常结果若为没有配置的 `proceeed`，则报告名称错误，
不能把拼写错误伪装成正常默认显示。`default` 也不是在缺失普通场景条目时逐项合并的补丁：
每次仅选择一个完整映射，未命中的部件按主插件契约恢复基础状态。

模型绑定是可选的：没有配置模型的信号仍能执行后端规则。但如果配置了模型，引用缺失时必须明确报错，
不能静默替换成占位模型并声称配置成功。

## 5. 线程和清理规则

显示不改变行车授权，也不能阻塞信号计算周期。模型加载和解析在工作线程上完成；结果安装前
还要确认对应的配置和世界仍有效，避免把编辑前的结果装回去。
模型内部的显示序号只用于舍弃旧画面，不写存档，也不是资源的身份。

插件正常停用时，先经过 Basic 既有的资源占用检查，允许停用后再清理显示。
强制停用仍按已有安全规则处理。删除模型实体与释放列车资源是两个不同操作，不能用前者代替后者。
停用 JavaRailways 主插件前，必须先停用 SimpleSignals 等附属插件并完成其显示清理。
区域线程删除模型可能晚于 `onDisable` 返回；应使用主插件显示服务的清理完成结果确认，
不能在物理或区域线程上阻塞等待。完整规则由上述主插件模型契约维护。

## 6. 配置或显示失败时怎么办

找不到轨道、位置超出轨道长度、模型不存在、正常外观缺少映射，都应拒绝这次模型绑定并记录具体原因。
这些错误不能改变既有行车授权，更不能让列车因此获得放行。

缺少 `default`、其值为 null、引用未知动画/场景或同一部件的场景选择冲突时，拒绝安装该模型绑定。
已知的正常外观映射同样在安装前检查；默认外观存在不能掩盖其他映射错误。
规则状态不可用时，选择上述 `default`。实体创建或线程调度失败时，报告显示故障并清理已创建部分，
不能把显示错误抛回信号计算回调。服务器也不能声称已经确认客户端资源包安装正确。

## 7. 性能开销在哪里

准备每个模型时，进行一次轨道 ID 查询、一次 `O(log N)` 弧长采样和模型解析；
N 是轨道曲线的采样点数。这不是每 tick 执行的流程。

处理一次信号结果时，成本为 `O(C + M)`：C 是变化列表或入口索引找到的候选设备数，
M 是比较这些设备场景映射所需的总条目数。只有实际改变外观、位置或旋转的模型才产生实体更新。
主插件可以合并尚未显示的旧画面，但不能合并或丢弃信号系统必须处理的安全事件。
加载时保存经过校验的不可变 `default` 和外观映射；选默认值为 `O(1)`，按外观名称查表为期望 `O(1)`。
这些选择不扫描全部模型，也不在状态变化时重新解析 YAML；完整场景比较和实体更新仍有上述各自的成本。

显示慢只让画面暂时落后，不让物理等待。大量加载或建造时的实际成本仍要测试，
不能因为更新队列有上限就声称所有操作都不会卡顿。

## 8. 具体使用情形

- **进路变化：** 规则给出新的外观名称，SimpleSignals 选择模型包中的对应场景，更新真实的多部件模型。
  进路预告机可以读取同一个逻辑源，但独立配置摆放位置。
- **只有限速变化：** 列车控制读取新限制；如果模型外观没变，不更新实体。
- **设备配置被替换：** 先关闭旧模型。旧回调后来完成，也不能覆盖新配置的画面。

## 9. 实现时必须验证什么

- 初始显示、外观变化、不可用状态，以及增删改模型绑定，都得到配置要求的结果。
- 验证无初始结果 → 普通外观 → `Unavailable` → 恢复普通外观的完整选择序列；没有额外信号事件时也能提交初始默认画面。
- 缺少/null/非法 `default` 拒绝绑定，显式 `{}` 恢复基础外观；未知普通外观名称报错，不静默走默认值。
  正常 0 速度输出及进路显示器的明确无进路外观仍按自己的映射显示；不向主插件通用模型增加此必填约束。
- 只改速度或显示器附带信息，而外观不变时，不产生实体更新。
- 旧回调、世界卸载/重载和插件停用不会留下或重新创建旧模型。
- 显示失败不影响信号安全输出；AB/BA 摆放与外观映射通过不依赖实体的计算测试。
- 用独立 Java 调用示例验证公开接口，另在实际 Folia 服务器中检查模型和资源包的显示效果。

## 10. 本批不改变什么，下一批还要确定什么

本批不改世界存档格式。以后增加可选模型绑定时，先检查字段默认值和它所属的独立存档格式，
不因为分批实现就连续升级版本，也不为开发中的接口草稿增加旧格式兼容代码。
`default` 的选择规则已确认；完整模型包配置、倾斜/偏移规则和交互建造字段仍需确定。
此次只更新契约和配置片段，不修改磁盘格式、增加版本号或为旧的 `unavailable` 草稿名称保留别名。

实现中不要每 tick 扫描全世界信号，不要在通用模型代码里写死灯色，也不要通过 SimpleATOBukkit 转发显示。
由 SimpleSignals 解释外观映射、提交变化后的模型数据，主插件只负责普通模型的构造与线程调度。
用一个普通物品充当单灯占位，不能算完成了这里要求的模型系统。
