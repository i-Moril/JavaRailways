## Findings

### Direction ownership and public prerequisite

- `SimpleATO/src/main/kotlin/work/art1st/javarailways/simpleato/routing/OperatingDirectionStore.kt:45-99` is the sole policy store: absent entry permits both, present `ViewDirection` permits exactly one. `put`, `restore`, `replaceRails`, and `entries` synchronize on one lock; there is **no policy revision/event**. `overlay` is internal and copies the whole store.
- `SimpleATO/.../SimpleATOWorldData.kt:25-31` already composes this store and `SignalEpochRuntime` in one world owner. Keep ownership here; do not create a Basic direction store.
- Existing public `InfrastructureResourceService.java:46` exposes topology, not direction policy; `RailwayObservationService.java:16-28` exposes completed physical observations, not operating policy. `SimpleSignalsHostServices.java:16-49` has no direction capability. Direct imports of `simpleAtoWorldData`/private Bukkit worlds are not an acceptable add-on seam.
- Mandatory small addition: a host read-only **requested-rail subset** snapshot through the existing infrastructure facade, supplied at existing world composition (`DefaultInfrastructureResourceService.kt:57-99`, `BukkitPlugin/.../logic/WorldManager.kt:170-202`). Validate requested rails against the captured exact topology; distinguish unavailable/unknown from known absent policy. Capture all traversals' policy in one store lock; per-rail calls could mix policies.
- Derive enabled/disabled status at prepare/bind and recheck the relevant subset at publication/admission. Compare single-direction policy with each normalized traversal's actual facing: A AB → B BA requires A AB and B BA. A missing entry is both, therefore mismatches a single block; bidirectional requires every traversal's rail policy to be both. Any one mismatch disables the entire block without rejecting its persisted definition.
- Mandatory notification prerequisite: central store mutation methods emit immutable **changed rail IDs**, including no-op suppression, to the already-owned signal epoch path. Existing `SignalEpochRuntime.kt:36-52,117-125,275-288` provides queued detached updates and rail→source watch indexing for admission changes; extend that bounded pattern for direction changes rather than polling global revisions or replacing every world's sources.
- Existing store mutation sites need not each acquire a new listener/token: centralize notification in `put`/`restore`/`replaceRails`. Owner composition can pass a change sink directly; public snapshot/event names are proposals, not frozen signatures. Restore before source install is covered by baseline; rollback/replacement changes must report final observed values.
- Existing authoring barrier: `BukkitPlugin/.../tool/RailObjectWand.kt:647-674,953-972` wraps direction set/remove in rail-scoped edit permits. Rail replacement/undo writers already use `replaceRails`/`put`; retain their barriers. Do not bypass them or release existing claims when disabling policy. Scope event handling via `FixedBlockReadSnapshot.blockIdsByRail` (`FixedBlockCatalog.kt:79-104`) and existing consumer graph.

### Reverse detection and denial: reuse failure mechanics

- `SimpleSignals/.../block/FixedBlockCatalog.kt:272-276` currently prepares reverse geometry only for `bidirectional=true`; `FixedBlockRouteMatcher.kt:61-67,111` skips missing reverse geometry/opposite facing. Thus false produces an empty contribution instead of denial.
- Small matcher prerequisite: retain/derive validated reverse **geometry** for detecting either traversal independently of permission. Enabled single blocks reject reverse passage; enabled bidirectional blocks match both; disabled blocks project both geometrical directions for fallback. Preserve existing full-route continuity validation before authority clipping (`FixedBlockRouteMatcher.kt:64-87`), route endpoint truncation, repeated visits, and rail-index candidate discovery. Do not turn every geometrical reverse into an allowed control entry.
- `FixedBlockRouteResourcePolicy.kt:43-54` already converts deterministic matcher rejection into an exception. Host authenticates contributor ownership (`DefaultInfrastructureResourceService.kt:228-251`). `Basic/.../RouteResourceAdmissionEngine.kt:316-320` translates callback exceptions to `INVALID_CONTRIBUTION`, before claim reservation at `415-423` and preparation at `440-444`. Physical compilation beforehand is validation only. Existing tail release at `279-282` can still legitimately advance the old grant; “atomic rejection” means no new claim/preparation or authority enlargement, not freezing independently eligible tail release.
- Reversal also collects/rejects contributions before rebasing (`RouteResourceAdmissionEngine.kt:639-663`). No new typed contributor result is needed unless product explicitly demands a distinct public failure code. Never encode policy rejection/train context into `ResourcePreparationDescriptor`.
- Selected-route apply can use the same policy validation in `FixedBlockInspectionSource.routeInfrastructureDependencies` (`:55-59`). Exceptions already abort dependency compilation (`InspectionRuntime.kt:79-86`) and roll back the guarded applied plan (`TimetableDispatcher.kt:4084-4098`). Validate enabled reverse denial here too; do not wait for first moving train.
- Disabled normal control should omit **new** fixed-block contribution/entry authority floors but retain definition/resource existence and any already-held token's original tail-release lifecycle. Basic physical resources remain independently mandatory. Whether applied dependencies retain the disabled block ID should be explicit; retaining it preserves existing plugin/edit protection without asserting normal block control.

### Fallback through the entire block; current gap and smallest extension

- Current entry-only path cannot implement this: `FixedBlockInspectionSource.kt:41-50` omits start-inside entries and projects speeds only from active declarations (`:65-95`); `InspectionScheduler.kt:205-230` drops passed triggers. Handler runs only baseline/set change/invalidation (`InspectionUpdate.kt:28-36`, `InspectionRuntime.kt:309-324`), so a handler-only “if head inside” test also cannot observe every exit reliably.
- Existing adapter already processes each cached restriction every control tick (`TrainRestrictionConstraintAdapter.kt:99-105`), and converts a passed `RouteSpeedRestriction` start into distance zero (`:169-174`). Therefore a **cached route-bound start/end speed value** can enforce braking toward entry, the nonzero cap after entry, and automatic expiry after exit without a second route scan, tick callback, or per-train resource.
- Bounded proposed extension: carry immutable route-bound range restrictions in the existing `InspectionDeclarationBinding` (or an equivalent binding-local callback result), merge them into the source's complete baseline/update snapshots in `InspectionRuntime`, and give the existing adapter an explicit end-boundary check. A nullable end on existing `RouteSpeedRestriction` or a separate range value are implementation choices; validate start ≤ end ≤ frozen route length and stable occurrence IDs. This is transient API data, not a persistence schema change.
- Plugin binding computes disabled-block windows once, in both geometrical directions, including routes starting/ending inside and repeated visits. Range values survive empty active declarations and expire using current head route progress in existing adapter apply. Boundaries/tolerance and whether the rear must also clear before lifting the cap need an explicit contract; current input only guarantees head progress. Do not claim “throughout” from a one-shot entry target.
- Avoid synthetic entry/exit declarations solely to force callbacks, a route-window map with another cleanup lifecycle, or full-route reprojection in updateHandler. Existing binding lifecycle already handles route replacement/reversal/removal.

### Known mismatch state versus unknown failure

- `SectionSignalState.Unavailable.effectiveSpeedLimitMetersPerSecond` is hardwired to 0 (`SectionSignalRuleRuntime.kt:22-38`). Reusing it for known direction mismatch would erase the approved nonzero fallback.
- Proposed plugin-local known-disabled state contains reason and fallback speed, distinct from unavailable; it has no fabricated model variant/aspect. Own range projection consumes this explicit cap only after valid topology/observation/policy proof. Missing/corrupt publication, unknown rail/store/plugin, stale topology and invalid stamp continue to fail closed at 0 (`FixedBlockInspectionSource.kt:77-95`, adapter `:128-148`).
- Current fact: downstream selection checks only `Unavailable` (`SectionSignalRuleRuntime.kt:264-280`) and then casts every remaining state to `Available` (`:289-293`). Adding a known-disabled state without changing this projection would fail the cast and become 0 via the existing catch; this is current behavior, not the proposed fallback design.
- Proposed downstream behavior: consumers must read the **known degraded section's effective limit** (configured fallback, default 20 km/h), preserving usable fallback through preceding valid signals. Do not equate known mismatch with unavailable and thereby force a permanent preceding stop. Unknown/missing/corrupt dependency still propagates 0. Adapt the existing rule input/projection to carry this known effective limit without inventing a national aspect or model variant; the precise state/input shape remains an implementation choice. Own presentation can use an existing configured/default presentation or no model, independently of the nonzero effective limit.
- Direction-change wakeup must update affected block status and propagate affected section/signal consumers in the existing epoch; `SectionOccupancyRuntime.kt:188-212` already atomically publishes signal values and returns declaration invalidations. Direction event capture/coherent publication ordering is a required test, not an assumed consequence of store synchronization.

### Configuration and installation

- No plugin operational config loader/resource currently exists: `SimpleSignalsPlugin.kt:23-40` loads host services and constructs manager; model-package YAML is a separate persistence boundary and is not the speed config.
- Add one plugin-local startup config field, proposed `disabled-block-speed-kmh`, default `20.0`; validate a finite positive number, convert once to `20.0 / 3.6` m/s, and inject the immutable value into manager/runtime/binding. No world-definition schema bump, old-data adapters, speed tables, or hot reload is required. A small `config.yml` plus startup value loader is sufficient; constructor defaults keep focused tests inexpensive while production injects real direction policy explicitly.
- Preserve host compile-only isolation: `SimpleSignals/build.gradle:28-32,132-148` forbids host classes in the add-on JAR. Existing direct `:Core/:Basic/:SimpleATO/:BukkitPlugin` API dependencies already cover the proposed values; add-on imports must remain public. Do not add another service hierarchy solely for this policy.

### Manual-control boundary

- **Subsequent user decision:** manual driving must remain unchanged; the degraded limit applies
  only to ATO. Do not implement the optional manual seams below, add automatic braking/ATS, or
  remove existing Basic manual safety behavior. They record the research boundary, not batch scope.
- **Current fact:** `Basic/.../control/RealisticManualController.kt:98-111` reads the world 0-speed safety interlock, then executes the player's handle directly; it does not consume SimpleATO inspection restrictions. SimpleATO's adapter is wired only by its controller (`SimpleATO.kt:630-661`). Thus the route-bound proposal alone does **not** enforce 20 km/h on manual trains. Spacing responsibility and overspeed enforcement are separate product decisions.
- Closest bounded generic seam if manual enforcement is required: a read-only current-position speed-cap callback injected at `RealisticManualController` composition, evaluated in its existing tick, which selects/coasts/brakes through the existing dynamics. Host composition sites are `BukkitPlugin/.../control/TrainControlManager.kt:128` and `.../command/TrainCommand.kt:434,913`. SimpleSignals can answer via its rail→block index and canonical head position; the public host must route that callback without Basic importing SimpleSignals/SimpleATO implementation.
- `TrainDynamicsExecutor.kt:32-52` is shared by actual manual/automatic handle control and is the nearest shared numerical step if a cap must affect both; currently it has **no speed-limit input**. Any extension must keep `preview` and `step` consistent and produce distance/state from the same dynamics. Simply clamp published speed after `train.moveTrainForward` would not constrain motion, and instant speed truncation is not a validated braking policy. Manual ahead-of-entry braking/position access and callback registration lifetime are unresolved prerequisites; this research does not claim an existing universal/manual limiter or approve new generic runtime machinery.

## Caveats / Not Found

- Source feasibility only; no runtime/build/test results, no final public signature, no implementation approval inferred.
- Existing direction reads cannot by themselves wake signal epochs or prove whole-traversal coherence. The bounded snapshot plus scoped change path must be included before promising live status correctness.
- Manual nonzero speed enforcement is explicitly out of scope. The final implementation proposal
  uses head route progress to end this speed restriction at the section exit; existing tail-clear
  resource release remains independent. This is an approved TARGET proposal,
  not proof of an implemented end-boundary check. Unknown failure is not the known-mismatch exception;
  known degraded downstream must remain usable at its configured effective limit.
