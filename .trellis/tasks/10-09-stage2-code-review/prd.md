# 全项目代码与文档审查（由 Stage 2 审查扩展）

## 目标

系统审查整个项目的代码质量、模块边界和文档一致性，而不仅检查 Stage 2 改动。形成可追踪的覆盖记录、问题清单及小批次修复建议，并单独判断哪些问题阻塞 Stage 2 正式游戏测试。不以新增功能或临时测试实现替代正式版。

- 用户于 2026-10-09 明确要求整个项目（包括 Basic、Core）纳入审查；沿用当前任务保留问题/提交历史，原有局部修复完成不代表整个模块审查完成。

- 同日追加：联结可指定主编组及结果方向，另一侧支持反向接入；解编可分别指定两个结果编组的运营方向，未指定时自动选择。两种操作均提供插件指定编组信息的事件；默认选择规则及事件技术合同见上述owner spec中的待审建议，尚未实现。
- 随后澄清：调用方即插件，联结由事件驱动，插件可按车钩兼容性等条件拒绝；未来SimpleATO监听事件，按时刻表等信息指定主编组并保留双方运营元数据供解编使用。撤回“调用方参数优先、监听插件仅补空值”的建议；Core不承担运营元数据的解释，具体合同统一见上述owner spec。
- 随后确认联结和解编均分为提交前决策事件与成功事件；插件可以拒绝，后续监听器不能撤销拒绝，只有成功提交后才更新正式运营记录。解编也必须允许车型/运营插件检查固定单元等限制，不采用“插件直接解编、无需前置检查”的中间提案。
- 后续批准方向设值冲突时拒绝；提交前监听器异常记录并继续派发但不提交，成功通知异常不回滚已完成操作。联结/解编接口及事件标记unstable，是正式能力但后续签名和语义可能改变。本批实现解编，联结事件须随完整联结事务接入，不以无生产入口的声明充数。
- 同日用户进一步确认保留 `PreTickEvent`、`PostTickEvent`、`RenderableEvent`，后续考虑接入而非删除；下一步转入 Core 代码改进。Core Seat 的处置仍未获确认。该次只记录决定与后续批次，随后用户批准开始首批 CR-022 构造失败清理修复；不连带批准其余批次或未决接口设计。
- CR-022提交后，用户批准继续修复所有没有争议的问题，并明确允许连续小提交后统一检查；可推进已确认的正确性缺陷及局部维护修复，不因此自行决定Seat去留、事件接入契约、联结/解编事务接口或持久化迁移方案。每批仍先说明目的/方法并单独验证，不合并成大提交。

## 范围与要求

CR-030后续确认（2026-10-11）：仅碰撞时尝试联结，由插件决策，不新增主动列车联结API；默认主编组优先碰撞前静止一方。车辆模型JS改为每节车厢独立状态，联结/解编不重建或合并双方JS，不中断已经接受的开门/延迟动作，旧命令不作用于新加入车厢。运营信息仍归运营插件。验收须证明两侧车厢状态、固定目标/物理侧与原操作完成结果保持；仅“主侧状态保留”不够。技术合同见[每车JS目标合同](../../spec/bukkit-plugin/backend/car-behavior.md)。后续已批准本批同时实施Bukkit与必要Core支持，collision联结拒绝/准备失败回退默认脱轨；主编组平局仍未冻结。实际实施状态与证据归执行计划，不以本需求段宣称完成。

1. 审查全部当前工程：Core、Basic、SimpleATO、SimpleATOBukkit、BukkitPlugin、SimpleSignals、ConfigLib、Annotation、BukkitPluginDev、TunnelBridgeBuilder、WebUI，以及构建/打包、仓库工具与四类文档。模块内部及跨模块调用链均在范围内，不局限于 Stage 2 diff，也不扩张为全仓功能重写。用户模型/生成物只检查引用和归属，不擅自删除或改写。
2. 核查旧代码的真实生产调用、测试和迁移用途，区分废弃路径与有意保留的公共 Java API，不能只依据语言或目录名称删除。
3. 核查模块归属、公共 API 签名、依赖方向、唯一状态所有者与关键调用链。
4. 检查格式、命名、错误处理、玩家文案和实际行为是否一致；识别重复模型及复杂状态机，不引入新的通用框架来掩盖复杂度。
5. 评估兜底的实际触发条件及保护的不变量；遵守已有 JS 无额外扫描/执行预算的决定，不误删 epoch、授权、并发发布或卸载安全校验。
6. 明确 Trellis、Dokka、网页文档和 `.codeabs` 的职责及交叉引用，并核对当前实现和 Stage 2 完成清单。
7. 每个问题记录证据位置、影响、优先级、建议和验证方式；区分游戏测试前阻塞项、可延期维护项和未确认线索。
8. 审查并删除或合并低质量测试：重点检查重复且无独立行为覆盖、只验证语言/框架机制、无有效行为断言、expected 与 actual 共用同一实现导致无法检出错误、仅锁定无契约意义实现细节的测试。不按测试数量或执行耗时直接判低质量；保留有效边界、安全不变量及历史 bug 回归。逐项记录删改理由和保留的等价覆盖，必要时先改写有效断言，再运行受影响模块回归。
9. 为各模块记录已检查的子系统、入口/调用链、源码和测试证据、检查深度及未覆盖部分。局部抽查、静态检查、可执行复现、模块测试和游戏现场验证分别标记；不得用测试通过或找到少数问题代替全面审查。

## 非目标与约束

- 用户于 2026-10-09 批准开始修复已知问题；部署和启动服务器仍不在授权范围。
- 后续修复须说明目的和方法，小批次提交并打开提交预览；2026-10-10用户批准无争议修复连续小提交、最后统一检查，取代此前每笔停下的节奏。
- 不把静态审查、单元测试或打包成功写成 Folia/客户端验证成功。
- 不升级未发布格式、不默认增加旧开发数据 runtime compatibility；涉及持久化时先阅读版本基线规范。
- 开发服 `192.168.1.230` 的存档须能手动迁移；暂不要求在插件 JAR 内打包自动迁移。格式变更前须取得一致的真实存档副本、核对来源格式，提供可审计、可 dry-run、保留恢复点的离线迁移工具或可重复操作步骤，并验证迁移结果。保留数据不等于冻结/发布 schema 基线，也不授权远端停服、部署或迁移；本轮尚未读取或验证该服存档。
- 保留现有脏文件、未跟踪文件和 docs-site 独立工作树；空目录不受 Git 跟踪，不为制造提交而添加占位文件。
