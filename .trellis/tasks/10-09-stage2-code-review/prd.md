# 全项目代码与文档审查（由 Stage 2 审查扩展）

## 目标

系统审查整个项目的代码质量、模块边界和文档一致性，而不仅检查 Stage 2 改动。形成可追踪的覆盖记录、问题清单及小批次修复建议，并单独判断哪些问题阻塞 Stage 2 正式游戏测试。不以新增功能或临时测试实现替代正式版。

## 背景

- 父任务：`09-18-signal-addon-implementation`；本任务不替代其剩余功能验收。
- 初始审查基线：`dev/signal-system`，`1f31961b`。已有只读初审结果保存在 `research/initial-findings.md`，后续必须对当前代码重新确认，不把线索直接认定为缺陷。
- 用户明确关注：空目录、遗留 Java（例如 AccelerateCommand）、四类文档职责、废弃代码、规范一致性、过度兜底、可读性与维护性。
- 用户于 2026-10-09 明确要求整个项目（包括 Basic、Core）纳入审查；沿用当前任务保留问题/提交历史，原有局部修复完成不代表整个模块审查完成。

## 范围与要求

1. 审查全部当前工程：Core、Basic、SimpleATO、SimpleATOBukkit、BukkitPlugin、SimpleSignals、ConfigLib、Annotation、BukkitPluginDev、TunnelBridgeBuilder、WebUI，以及构建/打包、仓库工具与四类文档。模块内部及跨模块调用链均在范围内，不局限于 Stage 2 diff，也不扩张为全仓功能重写。用户模型/生成物只检查引用和归属，不擅自删除或改写。
2. 核查旧代码的真实生产调用、测试和迁移用途，区分废弃路径与有意保留的公共 Java API，不能只依据语言或目录名称删除。
3. 核查模块归属、公共 API 签名、依赖方向、唯一状态所有者与关键调用链。
4. 检查格式、命名、错误处理、玩家文案和实际行为是否一致；识别重复模型及复杂状态机，不引入新的通用框架来掩盖复杂度。
5. 评估兜底的实际触发条件及保护的不变量；遵守已有 JS 无额外扫描/执行预算的决定，不误删 epoch、授权、并发发布或卸载安全校验。
6. 明确 Trellis、Dokka、网页文档和 `.codeabs` 的职责及交叉引用，并核对当前实现和 Stage 2 完成清单。
7. 每个问题记录证据位置、影响、优先级、建议和验证方式；区分游戏测试前阻塞项、可延期维护项和未确认线索。
8. 审查并删除或合并低质量测试：重点检查重复且无独立行为覆盖、只验证语言/框架机制、无有效行为断言、expected 与 actual 共用同一实现导致无法检出错误、仅锁定无契约意义实现细节的测试。不按测试数量或执行耗时直接判低质量；保留有效边界、安全不变量及历史 bug 回归。逐项记录删改理由和保留的等价覆盖，必要时先改写有效断言，再运行受影响模块回归。
9. 为各模块记录已检查的子系统、入口/调用链、源码和测试证据、检查深度及未覆盖部分。局部抽查、静态检查、可执行复现、模块测试和游戏现场验证分别标记；不得用测试通过或找到少数问题代替全面审查。

## 非目标与约束

- 用户于 2026-10-09 批准开始修复已知问题；部署和启动服务器仍不在授权范围。
- 后续修复须说明目的和方法，小批次提交并打开提交预览，等待用户检查后继续。
- 不把静态审查、单元测试或打包成功写成 Folia/客户端验证成功。
- 不升级未发布格式、不默认增加旧开发数据 runtime compatibility；涉及持久化时先阅读版本基线规范。
- 保留现有脏文件、未跟踪文件和 docs-site 独立工作树；空目录不受 Git 跟踪，不为制造提交而添加占位文件。

## 验收标准

- [ ] 上述八类范围均有审查结论；未确认问题明确标记，重要问题有生产调用或测试证据。
- [ ] 所有模块和横向范围均有覆盖记录；明确未检查部分，不将历史局部修复计为整模块审查通过。
- [ ] 低质量测试已删除、合并或改写，处置有理由和覆盖说明，不以减少测试数量为验收目标。
- [ ] 有可追踪的问题台账，列出游戏测试前阻塞项与可延期项，不能仅按文件长度或 Java/Kotlin 判断问题。
- [ ] 四类文档的职责和权威来源得到明确说明；过时内容及 Stage 2 清单有处置建议。
- [ ] 经批准修复的问题都有对应提交、必要回归验证和审查记录；延期项有理由和归属。
- [ ] 最终给出 Stage 2 是否可进入正式游戏测试的结论，以及仍需现场验证的事项。
