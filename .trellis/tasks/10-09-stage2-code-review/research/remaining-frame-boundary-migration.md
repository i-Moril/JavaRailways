## Findings

### Batch 4: Creation/destruction and maintenance placement

Files and actual call chains:

- `Core/.../physics/train/CoreTrain.kt:155–199`: constructor validates identity, creates TrainEnds, **registers train before extension initialization**, captures epoch-0 frame, transfers car ownership. Failure cleanup unregisters exact instance. Creation is not a detached prepare operation today; queue the entire constructor/initial placement/extension installation operation, not only final registration.
- `CoreTrain.kt:1222`: synchronous factory `create(...): CoreTrain`; persistence goes through `SavedTrainV1.load` and constructor. Preserve synchronous bootstrap ability, using coordinator scope rather than making loading depend on a host tick that has not started.
- `BukkitPlugin/.../command/TrainCommand.kt:292–331`: live creation is `CoreTrain.create -> setLocation -> TrainExtension.initialize -> speed profile registration -> commit -> publishCurrentTrainFrame -> renderer/player feedback`. Car creation/CarExtension initialization precedes this block. Move identity/occupancy revalidation and complete Core registration/placement into one operation; route player rendering and messages through existing entity dispatcher after result. Failure currently schedules `destroy()` and also immediately removes world entry: replace with one owned synchronous cleanup, not two conflicting cleanup paths.
- `BukkitPlugin/.../http/IsolatedTimetableSimulationFactory.kt:324–325`: simulation factory creates and sets head before simulation runs. `BukkitPluginDev/.../tests/PhysTestCommand.kt:188–189` is the third production-source explicit factory/initial placement call site. These three explicit `CoreTrain.create` production calls plus persistence and split construction must be inventoried; test fixtures are additional callers.
- `CoreTrain.kt:1142–1149`: `destroy(): Unit` currently queues generic after-commit work; `CoreWorld.kt:288–296 removeTrain(Train): Unit` removes registries/mailbox/ownership only, **not shared occupancy/world frame**. Normal command delete (`TrainCommand.kt:664–670`) clears control/profile/platform bookkeeping and reports success before destruction has happened. Queue complete deletion, and consume actual completion for feedback. Existing public `destroy(): Unit` compatibility/result choice needs explicit API design; no external repository plugins assumed by user.
- `CoreTrain.kt:307–371`: synchronous `setLocation`, capture/restore snapshot and `commitMaintenancePlacement` already own geometry rollback and no-teleport-sweep publication. However `setLocation` and restore can publish direction events before the complete multi-train placement is coherent. Do not wrap each car/train in its own boundary and call it atomic; retain one owner boundary across entire placement validation/rollback and publish only the final coherent batch before success events.
- `SimpleATO/.../timetable/TimetableInitialPositioner.kt:124–166`: captures snapshots, then **commits/enqueues each train before cross-train overlap validation**. Rollback restores trains but does not re-offer corresponding mailbox frames. Stage all placements, validate envelopes, then commit all and one shared refresh. Preserve initial plan rollback in `TimetableDispatcher.kt:479`; placement is part of `startTimetableEpoch`, not a standalone command.
- `SimpleATO/.../depot/DepotReset.kt:97,250–325`: synchronous `reset(...): DepotResetResult`, called from `JavaRailwaysCommand.kt:660`; already stages location/envelope checks before per-train maintenance commits, then applies Dispatcher/Depot ledger. Wrap the whole transaction, retain FAILED/PARTIALLY_COMMITTED and **ATO Stall** semantics. ATO Stall is not Core coordinator STALLED; normal frame-boundary gate remains usable. Do not silently add recovery support for a genuinely Core-STALLED coordinator, whose ticket/queue intentionally fail.
- `CoreWorld.kt:1220,1383,1501`: existing `rebuildSweptOccupancyIndex(epoch)`, `publishWorldFrame(epoch)`, `publishCurrentTrainFrame(id)` are sufficient builders. Reuse most recently completed epoch, refresh once after all affected train frames share it, enqueue only final frames; do not allocate fake physics epoch or invoke signal processor as a physical step. New train's revision-0/epoch-0 frame must be promoted to current completed epoch before world capture in a running world. Current `commit()` preserves its previous epoch, so creation-after-epoch>0 requires a deliberate owner publishing seam.

Lifecycle/order:

1. Add synchronous internal apply/refresh seam plus queued external result adapter; bootstrap/loading invokes same guarded apply before `start()`.
2. Migrate live create/delete and isolated/dev factory, then initial position/Depot reset as whole operations (can split as 4a and 4b).
3. Keep `WorldManager.kt:348–359 beginShutdown -> await exact ticket -> capture/save -> close` intact. Never schedule cleanup on rejected shutdown queue or drain mutations after final save. Existing runtime binding disposal is not per-train destruction.

Verification: existing `CoreTrainConstructionTest`, `CoreTrainPersistedPlacementTest`, `CoreTrainReversedPersistenceTest`, `WorldPersistenceRoundTripTest`, `TimetableInitialPositionerTest`, `DepotResetCoordinatorTest`, `WorldManagerUnloadTest`; extend behavioral cases for blocked create visibility, current-epoch creation, delete removes all observation/mailbox occupancy, failed multi-placement restores mailbox/world too, next physical step follows placement. Batch 4 is independently committable if it uses normal occupancy builder rather than uncommitted `prepareCouplingOccupancy`.

### Batch 5: External derail, manual turnout and prepared infrastructure edits

- `CoreTrain.kt:1167`: public synchronous `derail(reason): Unit` currently `awaitCurrentPhysicsEpoch` only, clears controller/motion and immediately swaps train frame plus Main event; shared world/occupancy remain old. Physics-origin path `markDerailedFromPhysics` + `publishPhysicsState` + pending notification is intentionally separate and must **not** queue/await itself.
- Production public-derail calls found: `WorldManager.kt:493` speed-safety request (already inside host between-frames scope); two collision LINK-failure fallback calls `PhysicsCoordinator.kt:784–785` (uncommitted batch 6). No other source call found. Preserve synchronous owner apply for host; external callers submit whole operation. Derail notification must see coherent zero-motion train/shared world publication.
- `Basic/.../infrastructure/ManualTurnoutSelectionRuntime.kt:20,39–125`: `select(...): ManualTurnoutSelectionResult` resolves selection, acquires claim, awaits, verifies root/physical lock intervals, applies and releases claim in `finally`. Constructor injected `awaitCurrentPhysics: () -> Unit` cannot enclose operation. Replace with enclosing owner-phase dependency, or guard synchronous Basic apply and adapt platform entry; don't merely replace await with a no-op. Keep claim + physical revalidation + apply/release together.
- `BukkitPlugin/.../api/internal/DefaultInfrastructureResourceService.kt:185,220,387`: adapter composes manual runtime and exposes **synchronous** `selectTurnout(pluginOwner,worldId,request)`. `WorldManager.kt:199` supplies await-only callback. `TurnoutWand.kt:219` is sole repository production consumer. Update Java service contract and wand result consumer together if returning Future; plugin enabled/runtime still-current checks must happen at execution, not only submission. Existing temporary claim semantics suffice; don't invent a second resource manager.
- `CoreWorld.kt:943–1043`: both topology transaction overloads (generic bootstrap/nested and prepared delta online) currently await-only before write lock. Shared coordinator enclosure outside topology lock gives one seam for **all** callers, preserving nested transaction handling, exact prepared root, declared delta validation and fault logic. Never acquire state gate/wait while holding topology write lock.
- `BukkitPlugin/.../tool/RailWandTopologyEditPlan.kt:89–95 commitTopology` delegates prepared Core transaction. `RailWand.kt` has **9** `commitTopology` sites (1474,1875,2241,2973,3750,4361,4633,4977,6019); expensive geometry preparation stays off-thread. Shared `prepareUndoAndCommit` at 4761–4813 owns edit permit + prepared undo cleanup for most edits. Queue **commit callback plus its live-root revalidation/permit release/failure cleanup**, not just inner rail install; otherwise surrounding metadata/undo effects escape the phase. Undo world restore has independent async path at 5890 onward ending in same commit seam. Metadata-only undo at 5862 doesn't enter Core structural transaction and must also get the outer owner phase when it changes runtime speed/signals.
- Manual turnout active selection is runtime, not structural topology revision. Refresh active-continuation/world observation with unchanged physical epoch before next operation observes it; do not fake structural revision. Signal/route processors' existing admission-update mechanism remains their owner responsibility.

Verification: `CoreTrainDerailEventTest`, `CoreWorldRailTopologyTransactionTest`, `CoreWorldTopologyStatePublicationTest`, `PreparedRailConnectionPlanTest`, `ManualTurnoutSelectionRuntimeTest`, `RailWandTopologyEditPlanTest`, `WorldManager*`; interleave main/timer wake in callbacks and prove no new physics, verify stale prepared plan fails without metadata/permit leakage, rejected manual selection leaves selection/claim unchanged. Batch 5 can commit before coupling by using existing normal builders and avoiding collision-specific code.

### Batch 6: Finish collision coupling and migrate split queues

- Existing uncommitted `Core/.../physics/train/TrainCoupling.kt:31–45` returns `Future<Train>` by generic after-commit task + `withStructuralMutation`. Replace scheduler only with coordinator queue; keep actual prepared collision contract and coherent occupancy commit (`:109–132`) rather than reimplementing solver/extension logic.
- `CoreTrain.kt:683–747 splitBefore(...): Future<Train>` is second structure operation using generic after-commit queue. Replace with coordinator owner queue, prepare both trains before install, publish complete shared occupancy/world and both mailbox frames before success event; current split success notification follows only per-train publication.
- `PhysicsCoordinator.kt:567–584 runEpoch` applies pending collision decisions on coordinator executor, not Main owner; physical DERAIL uses `markDerailedFromPhysics` correctly. LINK currently calls queueing `linkFromCollision`, then creates **generic postTick task** at 775 to `check(result.isDone)`/`get` and fallback derail under temporary structural scope. This depends on generic queue ordering. Replace LINK scheduling + real terminal result consumption/fallback with one frame-between owner operation, remove generic after-commit/postTick dependency; do not block owner awaiting its own queued work.
- Collision decisions require preservation of captured prior frame, topology revision and envelopes (old draft fields at coordinator PendingCollisionDecision). Keep detection/physical freeze in physics path; only structural apply and Main notifications run owner. Take care finite-batch queue means submission from success event is naturally deferred to next host batch. Success listener requesting rename must finish on that later batch; don't drain recursively or call `.get()` in listener.
- `CoreTrainCollisionCouplingTest` and `TrainCoupling` are uncommitted large draft; commit them only with all required CoreCar/CollisionEnvelope/CoreWorld helpers and result-consumption changes. Earlier batches must stage selected overlapping hunks, not entire `CoreTrain`/`CoreWorld`/Coordinator files.

Verification: existing split event tests, `CoreTrainCollisionCouplingTest`, CollisionEvent tests and coordinator tests; four end combinations, stationary admission, veto/extension failure fallback, renamed collision participants, success callback queued rename, corrected path retained, no moved car on rejected preparation, no stale frames/retired ownership, untracked WIP tested in exact staged candidate. ## Caveats / Not Found

- No external references needed; no internet lookup, Git operation, deployment or tests performed for this research.
- Counts above are production Kotlin call sites located by `rg`, not proof that arbitrary external plugins cannot invoke public APIs. Java public `selectTurnout` is explicitly included.
- Public synchronous `destroy/derail/selection` results need coherent handling: simplest is synchronous guarded apply for internal owners plus explicit queued adapter returning Future, not silently async Unit with immediate success reporting. This is an API implementation choice within approved migration, not a new operational policy.
- Existing ATO-stalled reset is supported; **Core**-STALLED recovery is not. If live recovery of failed Core physics is desired, that is new policy/authority, not an automatic exception to the current fail-closed gate.
- Full detached train construction and general transaction/notification framework are not required merely to avoid physics overlap; preserve current concrete owners and prepare/validate-before-publish order.
