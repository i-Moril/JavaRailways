# Station hook runtime research (read-only product inspection, 2026-10-25)

Scope: current Dispatcher, cursor, operation tickets, actual simulation adapters; no product edits or tests run. Requirements come from current prd.md. Recommendations below are a design proposal, not unapproved implementation or resolved product decisions.

## Verified integration points

- `SimpleATO/.../timetable/TimetableDispatcher.kt:1494-1536`: existing door-operation polling and BERTHED -> implicit open -> DWELLING. Arrival subtree currently starts **after successful open**, at `enterStationDwelling:2332` or `enterDestinationDwelling:2411`. New editable arrival entry must start at actual stopped/BERTHED publication **before implicit door opening**; move OpenDoors into the default authored definition and remove old unconditional automatic opening/closing paths for the new model.
- `:1536-1582`: departure logic presently conflates minimum dwell, next root action tick, implicit close, and terminal detection (`nextActionTick == null`). R1/R3a require explicit ORIGIN/STOP/TERMINAL/PASS call roles and explicit planned departure, not infer terminal from root suffix. A terminal run can have a following duty action; that is not another departure preparation.
- `scheduleStationCallSpec:962`, `startMovementPlan:5103`, `ActiveRun:6378`: bind per-stop runtime identity once from the compiled run-call metadata. Origin requires stationary acquisition/Check or preceding-run completion proof and a preparation-only invocation; it cannot wait for a future arrival event. Canonical operational destination/station identity must bind definition lookup, not station display name.
- `:2172-2595`: existing begin/process Station/Destination operation functions own a single implicit door phase and use run.state to interpret completion. They cannot serve arbitrary parallel authored operations unchanged. Extract/reuse their gateway request/ticket identity, timeout, snapshot and cancellation checks with task-local continuation, preserving Basic holds.
- `Basic/.../api/operation/TrainOperation.kt`: request captures requestId/serviceRunId/stationCallId/trainId/missionRevision, ticket confirms completion not queue acceptance. API has no estimated duration or persistent door-state query. `DoorSide.NONE` cannot construct OpenDoors/CloseDoors; explicit door block on a doorless stop needs defined semantic successful no-op without gateway call.
- `BukkitPlugin/.../operation/BukkitTrainOperationGateway.kt` and `SimulationTrainOperationGateway.kt`: both perform actual per-car behavior batches. Simulation executes captured JS and async completion, not a fixed-duration approximation. `SimulationTrainOperationGateway:24-33` also independently invokes `onReverse` through the real event bus; reverse safety must account for this event's asynchronous behavior if its completion is required by program semantics.
- `TimetableProgramCursor.kt`: immutable cursor supports one active branch and one successor; `ActiveRun` has one `extensionAction`, reverse operation and wait fields. New nonblocking children require per-task cursors/waits/tickets. Reusing these run-global slots would overwrite concurrent operations or allow one child to release another child's wait.
- `beginReverse:2597` / `processReverse:2650-2802`: reverse requires real stationary publication, suspends Basic release, prepares ATO, reverses once, waits for publication, rebases exact retained grant/body, restores protection, then calls root `advanceService`. Completion needs a task-local successor callback. Existing reversal also retires the active ATO StationCall, so station runtime/berth/door evidence cannot simply be assumed unchanged afterward.
- `SimpleATO/.../timetable/simulation/IsolatedTimetableSimulation.kt` and `BukkitPlugin/.../http/IsolatedTimetableSimulationFactory.kt`: retain same Dispatcher and real operation gateway; hook task progression belongs in Dispatcher tick after coherent physics publication. No wall-clock scheduler or separate simulation interpreter.

## Minimal robust runtime shape

1. Compile a shared station-program binding per timetable + canonical station, with two root entries and preparationLeadTicks. Resolve/freeze program snapshots at compile/apply. Stop invocation identity includes service cycle + runId + callId. Every stop gets fresh task state even when it shares a definition. Remove the old per-call ARRIVAL execution path rather than layering a competing second implementation.
2. Add a bounded station invocation runtime owned by ActiveRun/Dispatcher (separate pure task engine file recommended). It owns arrival root and preparation root plus finite spawned descendant tasks. Each task has its own immutable program cursor, actual relative-wait deadline, absolute timetable wait, optional ticket/continuation, and explicit RUNNABLE/WAITING/SUCCEEDED/FAILED/CANCELLED state. Tick tasks deterministically by stable creation ordinal, with a finite transition budget and bounded count/depth; never recurse without limits.
3. Entry rules are explicit: origin starts preparation at its due time after stationary acquisition; intermediate starts arrival after actual stop and starts preparation when arrival **root** succeeds and `elapsed >= departureTick - lead`; terminal starts arrival only; pass creates no invocation. A passed preparation deadline means immediate eligible start. Use checked timetable-cycle tick arithmetic, not machine time. No negative-tick representation or guessed reverse-time block.
4. Nonblocking container creates a child and immediately advances its parent. Child descendants remain owned by invocation. `wait task` joins a specific invocation-local handle and propagates failure/cancellation. Arrival root completion may release preparation while arrival descendants still run. **Departure/terminal handoff barrier** joins both roots and every descendant; only then apply min dwell/time/safety gates.
5. Prefer explicit END as a root-only final terminator, forbidden inside spawned children; statically require every branch path to reach exactly one END and forbid reachable trailing steps. This is a recommendation requiring final contract, not a settled product choice. END is a request to finish; it cannot mark invocation/service completed before descendant join. Avoid task wait cycles through structural scope/dominance checks or explicit validation, and keep runtime cycle detection/fail-closed as a backstop if references are dynamic.
6. Editable Open/Close/Reverse actions need deterministic internal resource ownership. Do not expose Mutex to player. Serialize overlapping door operations and reversal with one train-operation lease; passive waits/display can overlap. Otherwise parent and child may race close/open or reverse a captured physical side. Reject impossible order/wait cycles rather than silently canceling an earlier operation.
7. Track door-safety evidence separately from run.state: most recent successful commanded close for the current invocation/train orientation and no later successful/pending open, plus all relevant tickets settled. Merely seeing a CloseDoors block somewhere is not movement proof. Doorless stop is vacuously secured. Keep existing ATO departure/Basic authority/berth-tail gates; custom programs cannot grant movement. A terminal END does not require close by default; next duty movement must establish its own door safety before installing/releasing motion. Terminal optional departureTick gates handoff only and never implicitly runs preparation or closes doors.
8. Minimum dwell is an invocation deadline, not a task wait variable. Existing minimum dwell begins at actual open-success; with editable programs that never open, its anchor must be explicitly chosen in final design (actual stop recommended for such programs; open-success for default behavior preserves current semantics). Never make departure preparation start wait for min dwell: its close operation should overlap the remaining dwell when configured early, while final release still obeys dwell.
9. Keep tick-zero compiled inline steps from generating fictitious lateness. Relative waits start on task execution; absolute waits use the shared cycle-relative timetable clock and already-past targets complete immediately. Add entry due time to diagnostics independently from normal root movement lateness; graph event references must resolve to authoritative event time at compile rather than duplicate arbitrary numbers.

## Preparation duration evidence

No estimate API exists on TrainOperationGateway; tickets expose only state/message. Model actions run JS and may branch/call asynchronous animation, so a reliable duration cannot be inferred from an animation clip length. Use an explicitly configured preparation lead (with clear editor default) for MVP. If automatic default lead is desired, add optional declarative model close-duration metadata and label it an estimate, used only for scheduling, never as ticket completion evidence. Both live and simulation continue to await real completion. Arbitrary custom program duration must remain user-configured.

## Failure / reverse pitfalls

- STOPPED/FAILED/cancellation cannot be counted as successful task completion. Stop/transfer/unload must iterate **all** pending task tickets; cancellation confirmation failures retain hold/resources and current diagnostic recovery behavior. Current `cancelExtensionAction` knows only one run.extensionAction, insufficient for task tree.
- Never add sequential stopKey for station child wait/extension and forget it on same-mission departure; current arrival implementation deliberately avoids this. Hold ownership must be invocation-level, removed once after final gates, never by an individual child.
- Reverse cannot be a simple `train.reverse()` inside extension. Preserve publication+body-rebase+grant edit protection contract. Reversal inside an intermediate station may invalidate the originally planned onward direction and approach proof. Compiler must reject a mismatch or regenerate the explicitly reversed onward movement proof; no fresh opportunistic route search at runtime.
- Origin station currently has no active StationCall mission identity. Generalize zero-motion operation request identity to invocation identity without fabricating a running mission. Inspect gateways: they consume actual train/model and request identity; preserve nonnegative revision and stable IDs.
- Root terminal `completeOpenTerminalStation/Destination` currently sets entire service COMPLETED. New terminal hook must instead complete the **current run segment** and resume later duty actions after optional time. Never consume next run implicitly; authoring duty sequence remains authority.
