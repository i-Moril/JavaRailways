### BUK-01 P1 persistence: restart resets pair revision and loader selects stale backup
Location: BukkitPlugin/src/main/java/work/art1st/javarailways/bukkit/logic/WorldManager.kt:720 (captureSnapshots); reset at 82; loader BukkitPlugin/src/main/java/work/art1st/javarailways/bukkit/persistence/WorldPersistence.kt:58-71.
Trigger: previous session saved revision 10000; restart creates serverTickIndex 0; administrator edits, then shuts down before first periodic save (e.g. at tick 100). Shutdown capture writes primary revision100 and rotates revision10000 to .bak. Next loader chooses highest matching pair, so selects revision10000 backup and silently rolls back all latest changes. A crash after first periodic new save also reproduces. Two successful new saves rotate old backups away, but does not protect the common short-run/first-save window. No initialization from loaded revisions or separate per-world monotonic persistence sequence exists. Revision also repeats for multiple captures within one tick, so cross-file matching cannot distinguish all captures.
Contract: spec interaction-render-persistence says newest matching primary/backup pair. Pair serial numbers must preserve save order across host restarts. Minimum direction: independent persisted monotonic capture serial, initialized from existing pair, not host tick count; no schema bump implied. Existing WorldSnapshotExtensionDataTest checks equality and DTO roundtrip only, not host restart+rotation.

### BUK-02 P1 lifecycle: cancelled world unload destroys a world that stays loaded
Location: BukkitPlugin/src/main/java/work/art1st/javarailways/bukkit/logic/WorldManager.kt:468-470.
Trigger: any other plugin cancels WorldUnloadEvent before or after this default NORMAL handler. Handler has no ignoreCancelled and performs full unregister/save/worker close immediately. Bukkit keeps the physical world loaded, but no WorldLoadEvent follows, so JavaRailways runtime disappears permanently until manual reload. MONITOR-stage confirmed noncancelled handling is required; merely ignoreCancelled at NORMAL does not cover later cancellation. SimpleSignals has same issue (peer reviewer). HTTP map invalidation handler similarly observes cancelled unload but lower impact.
Contract: shutdown only on actual world retirement. Existing unload tests invoke unregister directly and miss event cancellation/order.

### BUK-06 P1 availability: unbounded in-process timetable JS owns compiler permits indefinitely
Location: BukkitPlugin/src/main/java/work/art1st/javarailways/bukkit/http/TimetableScriptSandbox.kt:101-114; BukkitPlugin/src/main/kotlin/work/art1st/javarailways/scriptworker/Main.kt:14-33.

Engineering evidence: docs-site/docs/timetable_js_syntax.md:86 still promises isolated per-call worker JVM, 64MiB heap, 128MiB metaspace, 3-second force stop and no uploads, opposite to current implementation/HTTP save. ### BUK-08 P2 Inline part YAML applies the same transform twice
- Location: `BukkitPlugin/src/main/java/work/art1st/javarailways/bukkit/config/model/PartRegistry.kt:258-261`; consuming merge `ModelTreeBuilder.kt:210-234`.
- Trigger: an inline part declares a nonzero `offset` or `rotation`, e.g. x=1 / yaw=30 degrees. `parsePartDefinition` reads that transform into the inline `PartDefinition`; `parsePartList` also copies the identical values into its enclosing `PartRefEntry`. `buildPart` unconditionally sums definition and entry transforms. The resulting local transform is x=2 / yaw=60 degrees. Imported references legitimately have two distinct transforms; inline YAML has only one declaration.
- User consequence: valid inline model pieces, including nested train parts, are misplaced/rotated. Keep transform ownership on either definition or reference once for inline entries.
- False-positive check: actual parser-to-builder chain traced, not inferred from naming. ModelTreeBuilderTest 57-98 constructs inline PartDefinition manually with zero own transform and nonzero entry transform, so its positive assertion bypasses the faulty YAML path. No runtime test run.

### BUK-09 P2 Train model construction abandons allocated visuals on partial failure
- Location: `BukkitPlugin/src/main/java/work/art1st/javarailways/bukkit/config/model/ModelTreeBuilder.kt:129-130,146-147,187-193`; car aggregate `extension/train/CarExtension.kt:389-392`.
- Trigger: first train part creates a visual successfully, but a later backend create/root create throws (production native backend performs Bukkit `world.spawn` at NativeDisplayRenderBackend 22-40; this is a real allocation/failure boundary). `entries.map` never returns its partially built models, and root creation has no catch/cleanup for completed children. Likewise a later bogie build failure abandons earlier bogies in map; body is already assigned, but `TrainComponentExtension.ensureModelBuilt` 115-122 leaves modelBuilt=false, and a subsequent retry overwrites bodyModel.

The ordinary model construction path in the same builder 88-120 already tracks createdVisuals and destroys in reverse order on failure; car/bogie construction bypasses that pattern.
- False-positive check: CarExtension.buildModel 359-366 reports and rethrows only. No outer transactional cleanup of unreturned children exists. This is a statically confirmed conditional failure-path defect, not an observed Bukkit spawn failure or measured leak. No test injected or executed. Scope can be presented as engineering/failure-handling issue if parent wishes to reserve runtime findings for reproduced triggers.
