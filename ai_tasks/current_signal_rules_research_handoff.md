# JavaRailways 当前信号规则：供各国标准调查使用的临时 handoff

日期：2026-10-05。依据 `dev/signal-system` 的当前代码核对，HEAD 为 `39a235d0`；最近功能提交为 `6ee799fb`。

这是一份可独立阅读的研究背景，不是新的实现合同。请不要假定已经符合任何国家的铁路标准。
调查范围是固定闭塞、保护区域、进路选择及它们向列车提供的速度限制。
不讨论模型包、外观映射、模型兼容性、实体摆放或渲染；文中的“红、黄、绿”只指信号语义示例。

## 1. 项目目标和取舍

这是 Minecraft 铁路插件。我们希望正确、性能可控、易于建造和扩展，不追求完整复刻真实铁路设备。
手动驾驶暂不新增 ATS 等强制信号保护；下面的自动制动和资源申请主要用于 ATO 自动驾驶。
若调查发现缺少真实系统的功能，请区分“影响游戏中正确性的问题”与“可以有意省略的拟真功能”。

模块职责如下：

- Core 提供物理轨道连接、几何和道岔实际连接方向。
- Basic 提供物理占用监测、公共运营方向、资源互斥申请和列车车尾通过后的释放。
- SimpleATO 沿预先冻结的行车路线申请资源，合并授权边界、前车和运营限制，用制动曲线控制车辆。
- SimpleSignals 是独立信号插件，定义闭塞和保护区域，选择进路，计算信号规则，再向 SimpleATO 提交附加限制。

信号只能使 Basic/ATO 已允许的运行更严格，不能凭一个允许信号越过资源授权边界。
当前不会在列车运行时让信号规则重新寻路；已应用的时刻表和运行占用会保护相关线路，禁止随意编辑。

## 2. 两种不能混淆的“占用”

**物理占用**：列车车身是否与某个区间重叠，由 Basic 的区间监测得到。列车进入和离开事件都带边界信息。
没有收到有效的初始观测，不能把区间当作空闲。信号规则读取区间内的列车身份集合及区间长度。

**资源持有**：列车提前取得某个资源的使用权，可以在车身进入前已经持有，停车时也可能继续持有。
资源由 Basic 原子申请；列车车尾通过相应释放位置后，由既有释放队列处理，而不是信号规则自行释放。

因此，“没有车身”不等于“其他列车可以申请成功”，信号外观也不是资源授权本身。
当前普通固定闭塞规则主要检查物理占用及下游信号，不把所有资源预留都直接翻译成灯色。

## 3. 固定闭塞的范围、方向和资源

一个闭塞是一条明确、有序、连续的轨道路径，可以跨多条轨道，但不得经过道岔，包括道岔直向。
闭塞和保护区域不得有内部重叠，可以共享边界位置。菱形交叉不会让寻路跨到另一条线路。

闭塞作为排他资源参与申请，而不只是一个速度牌。相向列车申请的是同一个区间资源，不是各方向各有一份资源。
信号是否存在，不改变这个区间仍需正常申请资源的事实。

- 单向闭塞只在正确方向的真实入口声明提前检查和资源申请要求；反向进入明确拒绝。
- 双向单闭塞允许从两端进入，仍使用同一个资源，**当前共享一份主信号规则结果**。
- 区间每段的实际行驶方向必须与 Basic 保存的运营方向一致；双向闭塞要求每段都允许双向。
- AB/BA 是每条轨道自身的坐标方向，并不等于全世界的上行/下行。连续路径可以由某轨道 AB 接到另一轨道 BA。
- 任一轨道方向失配、连接破坏或区间失效，整个相关闭塞禁止 ATO 进入，保留配置供修复，不降级成低速通行。

两端独立规则、单线多闭塞的运行方向协调尚未实现；不能把现有双向单闭塞概括成完整单线自动闭塞。
列车可从闭塞内部停车点起步或在停车点折返，原来持有的资源不先释放再重抢；新资源从车头前方申请。
一条路线也可多次经过同一个区间，每次经过的位置不同，但物理资源身份不变。

## 4. 当前固定闭塞规则究竟如何计算

当前内置的是 **JSON 配置的限速阈值表**，不是某国信号制式，也不是已实现的 JS 脚本接口。
输出包含有限、非负的目标速度（代码单位 m/s）和一个不透明的信号状态名称。
状态名称可以被作者定义为红、黄、黄绿、绿，但 Kotlin 不认识这些颜色的含义，也不会据颜色猜速度。

配置包括：

- `occupiedOutput`：受控区间有物理占用时的输出。
- `clearLevels`：受控区间空闲时，按下游有效限速选择的输出档位。
- `downstreamSignals`：明确配置的下游信号依赖，可以有多个。
- `inspectionLeadTimeSeconds`：ATO 应提前多久开始关注该入口；前视距离由列车速度等条件换算，不要求固定距离。

在区间和依赖都有效的前提下，等价计算过程是：

```text
如果本区间有列车：
    使用 occupiedOutput
否则：
    取当前有效下游依赖的最小限速
    选择“阈值不大于此限速”的最后一档 clearLevels
    使用这一档配置的速度和信号状态
```

阈值必须严格递增，第一档阈值必须为 0。若没有配置下游依赖，则空闲时取最高档。
配置的依赖未知、没有有效观测、依赖不可用，或已配置的分支都没有实际开通，不会被当作“没有下游限制”，而是限制为 0。
“下游有效但输出速度为 0”和“下游状态不可用”是不同情况：前者仍可通过阈值表选出黄灯，后者不能继续正常选档。

依赖路径和距离在加载/编辑时准备。遇到有分支的道岔，配置需要说明所依赖的通路；运行时按道岔实际方向过滤。
保护区域可按不同固定进路配置不同的下游依赖，未选进路的依赖不参与当前判断。
因此不是沿世界每 tick 搜索“看起来最近的一台信号机”。

**现有规则的能力边界，调查时请特别注意：**

- 输入已有区间长度、下游距离和保护进路信息，但这份内置阈值规则只使用占用和下游最小速度，不自动按距离计算灯色。
- 多个依赖取最小速度，会丢掉各依赖距离、先后位置等信息；并不是通用的多短区间制动预告算法。
- 当前校验不强制 `occupiedOutput` 的速度必须为 0，也不强制各输出速度随阈值单调增加。作者通常应配置停车语义；资源互斥仍是独立保护。
- 区间信号状态是共享计算结果，不是为每列车单独执行一次规则。现有阈值规则不按车型、制动性能、目的地分别选择显示。
- 将来可能增加更丰富的 Java/Kotlin 或 JS/YAML 规则，但脚本接口和执行预算尚未定稿，不能把这种扩展设想列为当前已支持。

## 5. 目标速度和实际制动

信号输出速度表示列车到达逻辑入口位置时应满足的目标速度，不是要求列车在远处立刻降到这个速度。
SimpleATO 使用沿冻结路线的入口坐标，把信号限制与资源授权、前车、其他运营限制共同交给制动曲线处理。
速度为 0 表示不得越过该逻辑入口；入口前何时开始减速由制动控制计算。

检查提前时间控制何时关注入口、提前申请资源，不等于信号灯色算法，也不替代列车原有的前视和制动安全范围。
车头已经越过的入口不会因为它在车身后变红，就凭空成为车前的新停车点；内部起步也不补造车后的入口。

## 6. 保护区域和固定进路

保护区域用于一个道岔或整个车站咽喉。玩家放置指向内部的边界，系统识别由这些边界围成的内部轨道。
区域内部不是一段普通闭塞，列车按自己的入口、出口和完整路线通过，不能用“整咽喉只能一列车”的独占令牌代替。

区域内的进路需要哪些轨道、道岔、交叉等资源，由信号插件沿固定路线准备，并交给 Basic 校验、互斥申请和设备准备。
取得授权时所需新增资源一起申请；冲突或未准备好时不得只拿到一半就驶入。
设备准备可以需要时间，不假定道岔切换一定瞬时完成。不冲突的进路可以分别使用不冲突的资源。
当前没有完整的真实联锁侧面防护、接近锁闭、分段解锁等规则集；不应因存在保护区域就宣称全部已经实现。

新区域首次完整闭合时，为每个可达的有向入口—出口组合保存一条沿轨道距离最短的合法进路。
有多条通路时仍先保存最短路，标记相关出入口供玩家调整。玩家可以按道岔当前通路替换表内路径，保留进路身份。
修复已有区域不会自动覆盖原进路表。固定进路表一旦存在，区域寻路只允许表内完整路径。
手动禁用某条已记录进路的功能尚未设计/实现，不等于当前已经可以在编辑器里逐条关闭。

## 7. 三种保护区域逻辑

**固定进路信号**：绑定一条明确的进路，只判断这条进路的占用、物理开通及相关下游。
不因同入口当前选择另一条进路而自动改绑。它有自己的列车请求时须等所需授权准备好；没有请求时检查其物理通路，不要求它一定属于默认集合。

**当前入口信号**：绑定一个有向入口，按下面的优先级确定本次判断哪条进路。

1. 该入口有 Basic 当前正在准备或已经授权的列车请求时，选择请求指定的进路。
2. 没有请求时，选择作者配置为默认、经过该入口且沿途道岔确实开通的进路。
3. 两者都没有时，不选择任何进路，输出配置的停车状态，速度为 0。

排队但尚未开始的请求，以及失败/结束的请求，不压住默认进路。无法证明唯一当前请求时，不任意选择一列车放行。
请求正在准备时保留它的进路身份，不临时切回默认进路；相关出口的真实车尾离开证据用于清除该次请求关联。

**进路显示器/进路预告机**：只显示同一个入口所选的进路身份，不产生限速或资源授权。
现有后端有“进路 ID → 状态”的配置映射；玩家如何编辑这些绑定仍待讨论。

一个区域可配置若干条互不冲突、能同时物理开通的默认进路。
默认进路不申请资源，不建立永久授权，只观测沿途道岔是否正确；恢复设备默认状态由设备自己负责。
实际道岔碰巧开通的一条非默认进路，不会被当前入口信号自动挑作默认进路。

## 8. 保护区域信号不是出口信号的纯中继

当前入口选定进路后，把这条进路视为受控区间，读取进路占用及该进路的下游依赖，使用同类阈值规则。
它不要求每条进路都先存在一台独立信号机，也不只是复制出口的信号状态。

在进入正常规则之前，还有更优先的准备条件：

- 请求来源必须具有覆盖本区域所需范围的完整已生效授权，且道岔实际方向与进路一致。
- 默认来源不要求授权，但必须符合已配置默认进路及真实道岔方向。
- 无选择、选择不可用、进路未准备好等情况，输出停车限制；进路或下游不可用不能用旧允许状态代替。

对完整保护区域穿越，当前申请范围至少到区域出口。
若出口与冻结路线中**唯一、紧接的固定闭塞入口同点**，范围进一步延伸到该闭塞出口；列车申请这整个闭塞资源。
运营终点位于该闭塞内部时，距离范围不越过运营终点，但仍申请整个闭塞资源。
不是扫描出口附近任意多个闭塞，也不是无条件申请整条远程路线。

出口没有同点的固定闭塞入口时，当前下限止于保护区域出口。
连续/移动闭塞场景下如何保证出口后有足够车尾净空的完整策略仍未完成；不能说当前已自动取得“列车长度加余量”的后续范围。

## 9. 出口红、黄、绿时入口会怎样：两个层次

先假设进路准备条件满足、进路空闲、下游有效。作者可以配置：

- 出口红灯对应速度 0：入口黄灯。
- 出口黄灯对应某个受限速度：入口黄绿灯。
- 出口绿灯对应较高速度：入口绿灯。

这是四显示规则的**说明性配置示例**，不是某国标准、项目固定规则或强制速度表。
也可以配置红→红、黄→黄等其他对应；运行时实际比较的是速度阈值，不是灯色名称。

再考虑资源准备：若出口后的直接闭塞被另一列车占用，当前列车无法取得上述整体申请范围，
保护区域入口就必须保持停车，即使正常阈值表会把有效下游速度 0 转成黄灯。
没有列车请求、只观察已开通默认进路时，则不要求资源授权，可能仍按同一表显示黄灯。

这意味着当前机制可能出现“默认观察为黄、列车请求但尚未准备好时为停车”的差异。
请调查这种差异是否需要额外处理，以及“信号允许的进路范围”和“为避免车尾卡在咽喉而申请的范围”是否应分开。
不要把有效红灯、观测不可用、闭塞资源被预留、进路设备未准备好这四种状态混为一谈。

## 10. 更新方式与故障行为

占用变化、相关道岔方向变化、请求/默认进路选择变化或下游输出变化，触发相关规则更新。
构建依赖关系时拒绝循环；一次变化沿“状态提供者 → 依赖它的信号”传播，结果未改变就停止该分支。
不使用反复尝试直到稳定的循环求解器，也不每 tick 对所有信号、所有列车重新执行完整规则。
不过 Basic 的物理占用观测仍随物理周期推进；不能把“规则按需更新”误读为物理占用也停止更新。

一次信号更新使用一致的物理观测、道岔选择、占用和准入状态。
铁路计算不阻塞等待 Minecraft 主线程或显示完成。线路编辑先后台校验相关区间，修改无关线路不能使全世界信号失效。
失效区间保留配置供修复；规则异常、依赖无有效基线或未知状态，不能扩大运行许可。

## 11. 请外部研究者回答的问题

请依据各国官方铁路规则、运营机构技术文件或权威标准，选择有代表性的信号系统进行比较。
必须标明国家、运营机构/线路类型、标准版本和具体出处；区分国铁、城市轨道及速度制/进路制等适用范围，不概括成“全国都一样”。

重点调查：

1. 只靠本区间占用、下游信号的有效速度及距离，能表达哪些固定闭塞制式？哪些必须增加不同输入？
2. 下游停车时，上游显示注意、减速或停车各有什么前提？区间很短时如何连续预告制动？
3. 咽喉入口信号与出口信号是什么关系？进路准备、进路占用、出口后闭塞和接近锁闭分别影响什么？
4. 为确保车尾能够离开咽喉，是否必须一次取得整个后继闭塞？如何区分正常运行许可与出口净空保证？
5. 双向单闭塞共用一个规则结果有什么局限？单线多闭塞允许同向跟车时，需要哪些方向锁定及解锁条件？
6. 进路表示/预告、临时禁用进路和默认进路，能否在不增加重复资源管理器的情况下表达？
7. 按车型、制动能力、速度或进路分别显示时，哪些应属于共享信号状态，哪些应属于列车自己的运行限制？
8. 禁止循环信号依赖是否妨碍环线等实际线路？现实系统如何划分预告范围和打断依赖？

建议将结论分成：当前配置已经能表达；增加少量规则输入即可表达；需要新运营/联锁机制；为性能和游戏目标可有意省略。
请先分析本机制，再指出最小必要改动，不直接设计一套完整真实铁路联锁系统。
不要将这里的配置示例当成已验证的日本或其他国家标准。

已有离线自动测试不等于符合各国标准，也不等于真实服务器、客户端或大规模性能验证。
