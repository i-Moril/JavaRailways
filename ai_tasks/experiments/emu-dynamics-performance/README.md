# 车辆状态数组优化实验（2026-10-31）

本轮只优化隔离性能原型，不替换生产动力学，不改配置、存档、服务器或已提交的关门修复。原型不是经过真实车型标定的设备模型。

## 对照与改动边界

同一进程中重跑四组实现，而不是拿本轮结果直接除以上一轮的耗时：

- `baseline`：调用生产 `TrainDynamics.step` 的原有简化动力学；它与复杂原型物理行为不同，只作成本背景。
- `prototype`：原复杂原型，每步对五个逐车状态数组执行 `copyOf`。
- `fresh-arrays`：每步创建五个数组；由源状态直接计算并完整写入目标，不做预复制。用于隔离复制成本。
- `reused-arrays`：每个 Engine 预分配两组数组，逐步交替读写；公式、标量状态和结果对象与前两组保持一致。用于隔离数组分配成本。

三组复杂模型保留每车制动缸压力、电制动力、牵引力、指令延迟计时和上一条指令。压力施加/缓解、电制动低速衰减、电空配合、牵引限制、坡度/阻力/黏着/jerk及积分公式不作功能性优化。

复用结果是有寿命限制的借用：对应工作区再次写入后，旧结果不能作为独立快照持有。原始种子/实际输入不借用工作区；需要保留结果时必须深复制。这不是可直接公开给任意插件的不可变状态接口，也不是完整生产执行器。

## 验证与测量

测量前验证逐步状态/输出的一致性、原始输入不变、试算分支顺序独立、工作区隔离、混合档位序列和选档/恢复结果。具体覆盖及断言见 `EmuPerformance.kt`。保持原有缓解抑制牵引、最终能起步及制动停稳的基本自检；不宣称验证了真实设备精度。

测量范围：

- `step`：从固定场景快照推进一次纯动力学，不包括真实世界取数、轨道几何、碰撞及发布。
- `selection`：沿用前次实验的独立选档/恢复检查计算内核，初始档位为 N；不包括完整 SimpleATO 路线规划、制动包络和真实控制器生命周期。
- `recovery256`：强制推进 256 步的压力测试，不代表普通工况会触及上限。

4/8/16 节，牵引、定速选档、制动和缓解起步四种输入；256 步测试只用牵引输入。每个 JVM 共 108 个测试单元、每单元五次测量，共 540 条数据。三个独立 JVM 串行运行，总计 1620 条。

计时会消费选档速度和恢复步数，避免恢复计算因结果未使用而被 JIT 消除；step 和 recovery256 最终输出还会计算五个状态数组的校验和，三种复杂模型及基线采用相同消费方式。这会额外增加 O(车厢数) 的结果读取，256步压力测试只在末尾读取一次。上一轮只消费速度，原始记录保留，但不作为本轮直接对照。

prototype 计时调用完整保留的原始复制算法，仍从复制后的数组读取旧值，避免“复制后内容不再被读取”使 JIT 得到不同消除机会；fresh/reused 使用公式相同、直接读源写目标的算法。

每单元至少预热 300ms，采用与前轮相同的约 15ms 以上自适应批量（最多 1,048,576 次），每 JVM 随机化测试顺序。先对五次批量取中位数，再对三个 JVM 中位数取中位数；同时保存跨 JVM 的范围和同 JVM 配对比率。不作统计显著性或 p99 延迟声明。

512MiB 堆、G1；线程分配量来自 ThreadMXBean，含实验包装对象，不代表存活内存。GC 日志用于保留环境证据，不能直接把整轮 GC 次数归因于某一种实现。

## 复现

本实验的生产源码基线为 `0dbab292`（与原测量所记更早HEAD的TrainDynamics内容相同）。正式动力学更新后，应在该提交的独立worktree复制本实验目录并运行，不能在新模型上把当前 `TrainDynamics.step` 误标为旧基线。runner会核对记录中的基线源哈希。

在相应基线仓库根目录执行：

```sh
./gradlew :Basic:emuPerformanceClasspath --offline --no-daemon -I ai_tasks/experiments/emu-dynamics-performance/run.gradle
python3 ai_tasks/experiments/emu-dynamics-performance/run.py
python3 ai_tasks/experiments/emu-dynamics-performance/summarize.py
```

runner 默认创建 `array-optimization-run-2026-10-31`，已存在则停止，防止覆盖原始数据；可用 `--output` 指定新目录，汇总对应使用 `--input`。编译只通过临时 init 脚本增加实验 test sources，不改正常构建配置或生产源码。

第一轮数组试测被源文件哈希守卫判定无效：最后一处验证补充的编译与首个 JVM 启动重叠。其数据在 `discarded-pre-freeze-run-2026-10-31`，不进入汇总。最终轮冻结源码及编译 class，逐个 JVM 开始/结束都校验哈希。

原轮源代码、脚本、结果和说明完整保存在 `original-run-2026-10-31`，其中 Kotlin 文件使用 `.kt.txt` 后缀以避免参与递归编译。根目录原有 CSV/summary/environment 也仍是上一轮数据。本轮数据在单独的 `array-optimization-run-2026-10-31` 目录中，勿混用。

## 结果

三个 JVM 已完成，共 1620 条有效测量。最终数据、来源/编译哈希、编译和验证日志均在 `array-optimization-run-2026-10-31`。本机虚拟化环境为 Intel Core Ultra 9 275HX、8个可见CPU、OpenJDK21.0.12.1、512MiB/G1；不是开发服务器性能测量。

8 节编组，从 prototype 到 reused-arrays：

- 单步四工况耗时下降 11.4%～21.2%；牵引工况 0.103 -> 0.087 μs。每步分配 640 -> 240 B（下降62.5%）。
- 选档/恢复检查内核四工况耗时下降 41.4%～50.6%；牵引工况 2.641 -> 1.305 μs，每次分配10176 -> 3776 B。四工况分配下降62.6%～64.5%。
- 强制256步压力测试 26.010 -> 21.700 μs，分配157720 -> 55320 B。

16 节编组：

- 单步四工况耗时下降12.9%～23.7%；牵引工况0.195 -> 0.157 μs，分配960 -> 240 B。
- 选档内核四工况耗时下降46.0%～50.6%；牵引工况3.553 -> 1.755 μs，分配15296 -> 3776 B。
- 强制256步压力测试41.897 -> 33.072 μs，分配239640 -> 55320 B。

只取消预复制而仍创建数组（fresh-arrays）的分配量与prototype相同，耗时收益小于完整复用，且部分单步工况无收益。因此数组反复分配确实是这部分原型成本的重要来源，不能只归因于复制；尚未单独量化GC占比，也不能归因于设备模型本身复杂。数组复用使分配不再随每步车厢数线性增加，但对象/字符串/集合等残余分配仍存在。预分配工作区增加每个Engine固定内存，不等于零内存成本。

一致性验证：90组编组长度/坡度/初始状态组合，每组320步混合动作，三复杂实现逐位对照原始算法；另有打乱试算顺序、低速衰减边界、NaN污染目标缓冲区、1080次选档结果及步数比较、完整256步末状态比较、原始快照/跨Engine隔离和借用生命周期检查。独立只读复查通过。

不能由本实验推算服务器可承载列车数量；真实运行还包含ATO规划、世界/车辆取数、几何、碰撞和实体等工作。优化版仍是隔离原型，不能直接把借用状态交给生产持久化/并发消费者；生产替换、提交、部署均未进行。
